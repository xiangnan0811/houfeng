## 1. 设计阶段不应让多个版本同时充当开发基线

### 1.1 结论

> **可以保留历史，但不能让历史继续充当“当前开发基线”。**

也就是说：

- 历史版本可以作为设计决策记录保留
- 但开发人员只能对准 **一套当前有效的基线**

如果同时保留多个“都像当前版本”的页面稿，后续开发一定会出现：

- 页面 A 按旧稿实现
- 页面 B 按新稿实现
- 组件和壳层逐步分叉
- 最终还要返工统一

---

### 1.2 正确的分层方式

建议以后始终采用这三层：

#### A. 当前开发基线（唯一）
这是开发真正应该参考的那一层。

它应只包含：

- 当前有效的 Stitch 项目与选定屏幕
- 当前有效的视觉规范
- 当前有效的开发交付说明

#### B. 历史 / 审阅记录（可保留）
包括：

- 第 1 轮视觉评审
- 早期概念稿
- 被替换掉的方向稿

这些可以保留，但它们的角色是：

> **解释为什么演进到了现在这版**

而不是：

> **继续指导开发**

#### C. 后续方向 / backlog
包括：

- V2 / V3 方向
- 当前不纳入 V1 的候选能力

这层也不应参与当前开发基线。

## 3. 这套设计到底怎么用

### 3.1 不要只靠口头描述

后续开发不要只靠：

- “上次我们聊过”
- “我记得那张图大概是那样”
- “Stitch 里好像有一版更新过”

这会导致开发阶段不断回忆和猜测。

---

### 3.2 推荐的实际使用方式

最稳的方式是把设计交付分成三类材料：

#### A. 规范文档
作用：
- 定义产品边界
- 定义对象模型
- 定义状态、交互、视觉规则

这部分由当前 V1 文档包承担。

#### B. 视觉锚点
作用：
- 让开发知道页面应该长什么样
- 避免每个页面重新发明壳层和组件层级

这部分由 Stitch 项目和当前基线屏幕承担。

#### C. 可携带导出物
作用：
- 在新会话、新仓库、新开发阶段里快速复用
- 避免完全依赖在线项目状态

这部分建议在真正开始开发前导出并落地。

## 4. 导出时怎么选

基于当前 Stitch 的导出选项，不同格式的角色建议如下。

### 4.1 AI Studio
适合：
- 继续在 Google AI Studio 生态里做快速延展

不适合直接作为唯一开发基线，因为：
- 新会话未必天然知道你指的是哪个 AI Studio 产物
- 对开发 handoff 来说不够自描述

### 4.2 Figma
适合：
- 如果后续真的要走标准设计团队协作流程
- 需要更强的标注、量取、设计交付协同

如果当前主要是你 + Codex / Stitch，则不是必须。

### 4.3 `.zip`
这是**最推荐保留的一种可携带导出物**。

适合：
- 留档
- 新会话复用
- 放进新项目仓库作为 `docs/design/` 资料

因为它最便于：
- 本地保存
- 路径明确
- 被新的会话直接读取

如果已经像当前这样解压为本地目录（`_inbox/stitch_v1`），那么后续更推荐：

- 直接把解压目录中的有效内容搬进新项目
- 同时保留原始 `.zip` 作为归档备份

### 4.4 Code to Clipboard / Stitch React App
适合：
- 原型代码起步
- 看看 Stitch 生成的结构化前端表达

不建议把它当作“唯一设计真相”，因为：
- 代码导出更像实现草稿
- 不是最稳的视觉规范载体

### 4.5 Project Brief
适合：
- 做高层摘要
- 给新会话或新协作者一个快速入口

但它不足以替代完整设计规范与页面锚点。

## 5. 新会话中怎么继续使用这套设计

### 5.1 先接受一个事实

> **新的会话不会继承当前对话记忆。**

所以后续复用不能依赖：
- “你应该记得”
- “我们上次说过”

而必须依赖：
- 文件
- 路径
- 项目 ID
- 导出物

---

### 5.2 最稳的三种方式

#### 方式 A：直接引用当前 vault 文档
在新会话里明确告诉助手：

- 先读 `D:\notes\obsidian\_inbox\服务器舰队控制面-v1-设计总览.md`
- 再读视觉规范、交互原型、开发交付说明

这适合：
- 仍然在本机
- 助手可以访问这个 vault

#### 方式 B：直接给 Stitch 项目 ID / 屏幕 ID
在新会话里明确写：

- 参考 Stitch 项目：`projects/11890404311726538701`
- 优先参考屏幕：`f7b6...`、`e5b6...`、`c235...`、`7cd2...`

这样新的会话就可以直接读取当前视觉基线，而不是猜测你指的是哪版稿。

#### 方式 C：把导出物放进新项目仓库
这是**真正准备开发时最推荐的方式**。

建议在新项目仓库里建立类似结构：

```text
docs/
  design/
    v1-baseline/
      README.md
      screens/
      export.zip
      handoff.md
```

这样在新项目里只要一句话：

> 先读 `docs/design/v1-baseline/README.md` 和 `handoff.md`，再按里面列出的 Stitch 屏幕与规范开发

新的会话就能无歧义继续。

## 6. 我建议的“开发交付包”最小组成

如果后续真要进入开发，建议至少准备这一包：

### 6.1 必需
- 当前设计总览
- 交互原型文档
- 视觉规范文档
- 当前优先 Stitch 屏幕 ID 列表
- 技术选型文档

### 6.2 强烈建议
- 一份 `.zip` 导出
- 一份 `handoff.md`

### 6.3 handoff.md 应该写什么
至少写清楚：

- 当前唯一有效基线是哪组屏幕
- 哪些旧稿已被替代
- 中文主界面语言策略
- 页面壳母版是哪张
- 首页 / Node Detail / Target Detail / Onboarding 的参考顺序

也就是说，它要回答：

> **开发人员现在到底应该看什么，不该看什么。**

### 7.1 给新 Codex 的首条提示词模板

如果你准备在新的实施仓库里启动一个新的 Codex 会话，推荐直接把下面这段作为首条消息发给它：

```text
这是“候风（Houfeng Fleet Control Plane）”V1 的实施仓库。

先不要直接实现，先完整读取以下设计基线：

1. docs/design/v1-baseline/README.md
2. docs/design/v1-baseline/architecture-data-model.md
3. docs/design/v1-baseline/rules-and-interaction.md
4. docs/design/v1-baseline/ui-ux-spec.md
5. docs/design/v1-baseline/visual-review-round2.md
6. docs/design/v1-baseline/tech-selection.md
7. docs/design/v1-baseline/handoff.md
8. docs/design/v1-baseline/stitch/baseline-screens.md

补充约束：
- 当前 V1 的产品、交互、视觉设计都已冻结，不要重新发散 V1 一级能力。
- 当前产品命名已冻结为：候风 / Houfeng Fleet Control Plane。
- 当前唯一有效视觉基线是 Unified / Baseline 这组 Stitch 屏幕，不要回退到早期概念稿。
- 技术路线已初步选定为：Go 中心控制面 + Go agent + React/Vite 前端 + PostgreSQL。
- 这是实施仓库，不是设计仓库；先理解设计，再结合当前代码与仓库现状提出实施计划。
- 不要直接开始写代码；先扫描仓库结构、运行方式、现有代码入口和 git 状态。

然后按 superpowers 流程推进：
1. 先做 codebase/context scan；
2. 使用 superpowers:brainstorming，但只做“实施前 framing”，不要重开产品设计；
3. 输出当前仓库与冻结设计之间的差距分析；
4. 再使用 superpowers:writing-plans 产出实施计划；
5. 经我确认后再进入实现。

你的第一条正式输出应该包括：
- 当前仓库扫描结果
- 你已读取的设计基线清单
- 你理解的冻结约束
- 建议的实施切入点
```

这段模板的目标不是让它“重新设计一遍产品”，而是：

> **让新的 Codex 会话先把冻结设计当成既定前提，再用 superpowers 流程做实施级收口。**

---

### 7.2 给新 Codex 的补充口径

如果你想再加一句非常关键的强调，我建议补这一句：

> **如果你发现当前仓库实现与设计不一致，先报告差距，不要擅自改设计。**

这可以防止新的会话在读到一半时，自己把冻结设计重新打开。

## 8. 当前推荐做法（最终结论）

如果只收成一句最实用的话，我建议：

> **保留历史，但只保留一套当前开发基线；开发前把当前基线导出为可携带交付包，并在新会话中用“文档路径 + Stitch 项目/屏幕 ID + 本地导出物”三件套继续引用。**

换句话说：

- 历史版本可以留作记录
- 但开发只能对准当前 Unified / Baseline 稿
- 新会话不能依赖记忆，要依赖文档和可携带产物
