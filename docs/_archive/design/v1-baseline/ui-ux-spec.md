# 服务器舰队控制面 V1 视觉设计系统与页面规范

> 相关：[[服务器舰队控制面-v1-设计总览]]、[[服务器舰队控制面-v1-详细设计-交互原型与操作流]]、[[服务器舰队控制面-v1-详细设计-异常、交互与默认规则]]

这份文档的目标，是把 V1 里原本偏结构和行为的设计，补齐为一套：

- 可统一主题
- 可统一页面布局
- 可统一组件风格
- 可统一危险操作与状态表达

的 **视觉与 UI/UX 基线**，避免后续开发时每个页面各长各的。

---

## 1. 视觉层在 V1 中的角色

虽然 V1 的架构、对象模型、异常规则和交互主路径已经比较完整，但如果缺少视觉层基线，后续开发仍然会面临这些问题：

- 首页、列表页、详情页的信息密度不一致
- 状态颜色与危险操作语义不统一
- 抽屉、确认弹层、危险区的样式逐页漂移
- 页面虽然功能正确，但看起来不像一套系统

所以这份文档要解决的不是“美化”，而是：

> **让 V1 从“能定义行为”升级为“能统一呈现”。**

---

## 2. 视觉北极星

我建议把这套系统的视觉气质定义为：

# **冷静、克制、高密度、工程师长期使用友好**

它应避免两种错误方向：

### A. 不要做成“大屏监控中心”
- 不要夸张渐变
- 不要炫技图表
- 不要信息巨大但不利于操作

### B. 不要做成“普通 SaaS 管理后台”
- 不要过于白盒卡片化
- 不要所有页面都像 CRUD 后台
- 不要让信息密度低到需要翻很多层

更准确地说，这套系统应该更像：

> **一个被长期使用的工程工具，而不是一个“看起来很新”的产品壳子。**

---

## 3. 主题策略

### 3.1 总体策略
我建议 V1 采用：

- **dark-first** 主题基线
- 同时在设计语义上允许未来扩展 light theme

### 3.2 为什么 dark-first 更适合
因为你的使用场景本质上是：

- 长时间查看
- 需要看大量表格、状态、时间线和趋势
- 多数情况下更像运维 / 观测工作台，而不是短时轻交互页面

所以深色主题更容易做到：
- 低眩光
- 高信息密度
- 状态色更清晰
- 时间线 / 趋势 / 异常更突出

### 3.3 背景与层级策略
我建议背景不是纯黑，而是：

- graphite / slate 系的深灰基底
- 用 **面层深浅差** 区分层级
- 而不是过度依赖 1px 硬边框

也就是说：

- 页面底色
- 一级容器
- 二级容器
- hover / active 容器

都应有清楚但克制的 tonal hierarchy。

## 4. 视觉令牌（Design Tokens）建议

下面这些内容不是给实现写死代码，而是给后续开发提供统一设计语言。

### 4.1 色彩语义

#### Primary
- 冷静蓝青色
- 用于：主操作、主要链接、激活态、当前视图强调

#### Success
- 柔和绿色
- 用于：正常、恢复成功、已恢复趋势

#### Warning
- 琥珀色
- 用于：关注、预警、风险上升

#### Danger
- 清晰红色
- 用于：告警、严重、危险确认、危险区

#### Muted / Secondary
- 中低对比灰
- 用于：次级文本、辅助元数据、归档与暂停类视觉弱化

### 4.2 状态色语义必须全局统一
以下状态的视觉映射必须一套到底：

- 正常
- 关注
- 告警
- 严重
- 维护中
- 暂停
- 已归档
- 已退役（当需要展示时）

我建议继续沿用当前文档中的状态语义：
- 正常 = 绿色
- 关注 = 琥珀
- 告警 = 红色系
- 严重 = 高对比红 / 强强调
- 维护中 = 偏蓝灰或次级强调
- 暂停 = 中性弱化
- 已归档 / 已退役 = 更弱的中性语义

### 4.3 字体
- 主字体：Inter 或同类现代无衬线
- 技术信息层（IP、延迟、ID、时间戳）建议使用 monospace

### 4.4 圆角与形状
- 中等圆角
- 整体偏理性，不消费化
- 不要过分圆润或“卡哇伊化”

### 4.5 间距系统
- 8pt spacing rhythm
- 高密度，但不能拥挤
- 页面间距和卡片间距必须全局一致

## 5. 页面布局系统

### 5.1 全局骨架
V1 建议统一使用：

- 左侧一级导航
- 顶部页面标题 / 摘要区
- 主内容区分块布局

也就是说，节点页、目标页、事件页、设置页都应该共享同一骨架。

### 5.2 布局优先级
我建议所有页面默认遵守：

1. **页面身份区**
2. **当前状态 / 当前风险区**
3. **趋势与上下文区**
4. **事件与历史区**
5. **低频编辑 / 危险操作区**

这样无论是 Node 详情还是 Target 详情，用户都会形成稳定心智。

### 5.3 密度策略
- 首页：中高密度
- 列表页：高密度
- 详情页：中高密度，但分区更清楚
- 设置页：中密度，不应像配置中心迷宫

---

## 6. 核心组件语言

### 6.1 状态标签（Status Pill）
这是整套系统最关键的视觉组件之一。

必须统一：
- 文案样式
- 颜色语义
- 边界与填充
- hover / disabled / maintenance 变体

### 6.2 摘要卡片
适用于：
- 首页顶部概览
- Node 当前资源摘要
- Target 当前状态摘要

要求：
- 数值层级清楚
- 状态辅助信息紧凑
- 不能像市场大屏 KPI 那样夸张

### 6.3 高密度表格
适用于：
- 节点列表
- 目标列表
- 执行节点视角
- Probe 列表

要求：
- 行高克制
- 对齐良好
- 状态 / 时间 / ID / 延迟一眼可扫
- 不依赖密密麻麻的边框线分割

### 6.4 抽屉 / 侧边面板
适用于：
- 标签编辑
- 轻量结构编辑
- 过滤条件说明

### 6.5 确认弹层
适用于：
- 维护
- 暂停
- 归档
- 退役
- 重置绑定

确认弹层必须统一包含：
- 当前状态
- 操作后状态
- 会发生什么
- 不会发生什么

### 6.6 危险区
适用于详情页底部：
- 删除
- 重置绑定
- 其他高风险动作

危险区应在全局视觉上明显区别于普通操作区。

---

## 7. 页面级规范

### 7.1 首页
必须体现：
- 系统总览
- 当前异常节点摘要
- 当前异常目标摘要
- 最近事件流

不应做成：
- 只会展示图表
- 没法快速点击进入处理对象

### 7.2 节点列表页
重点是：
- 筛选效率
- 状态可扫性
- 行内轻操作一致

### 7.3 节点详情页
重点是：
- 当前状态很清楚
- 趋势很清楚
- 异常原因很清楚
- 危险动作与普通动作分层清楚

### 7.4 目标列表页
重点是：
- 入口对象语义稳定
- Target 与 Probe 关系清楚
- 执行节点标签在视觉上可识别

### 7.5 目标详情页
重点是：
- ProbeItem 视图是核心
- 目标级趋势与多节点视角并列存在
- 当前问题与恢复路径清楚

### 7.6 事件页
重点是：
- 时间线感强
- 事件分类清楚
- 严重度、恢复、维护、通知相关事件容易区分

### 7.7 接入准备页 / 绑定冲突页
这是整套系统里最特殊的页面之一，必须保持：
- 安全感
- 操作路径清楚
- 冲突信息可对比
- 高风险动作明显隔离

---

## 8. UI/UX 统一约束

### 8.1 结构编辑与运行控制必须在视觉上区分
例如：
- 编辑名称 / 标签 / host -> 结构编辑
- 进入维护 / 暂停 / 归档 / 重置绑定 -> 运行控制

这两类动作不能在视觉上看起来一样重。

### 8.2 可恢复路径与不可直达路径都应可见
你之前已经明确偏好“显示但置灰非法项”，这条应延续到视觉层：
- 可恢复动作要明显可见
- 不可直达动作也可以显示，但需置灰并解释原因

### 8.3 空状态必须有引导，不只是空白
例如：
- 没有 Node
- Node 未绑定
- Target 无 ProbeItem
- 工作台视图无对象

都需要：
- 解释当前为什么为空
- 提供唯一最推荐下一步

### 8.4 图表只是辅助，不应主导页面
这套系统不是 analytics 产品，也不是大屏。  
图表要服务：
- 观察趋势
- 支撑判断

但不应抢走：
- 当前异常
- 当前状态
- 操作路径

## 10. 对开发前的建议

基于当前文字设计 + Stitch 概念稿，我建议在正式开发前至少再做一次：

### 10.1 视觉评审
重点看：
- 信息密度是否合适
- 暗色主题是否耐看
- 状态颜色是否足够统一
- 首页 / 节点详情 / 目标详情 / 接入准备页是否像同一产品

### 10.2 组件优先级确认
重点看：
- 状态标签
- 摘要卡片
- 表格样式
- 确认弹层
- 危险区

这些组件如果先定，后续页面一致性会高很多。

## 12. 视觉冻结基线（第 2 轮收口结果）

基于第 1 轮视觉评审结论与新增的 Stitch 全局壳层概念稿，这一节把当前需要冻结的视觉基线收成 3 条：

### 12.1 全局页面壳冻结

V1 后续所有主页面默认共享同一套壳层：

- **固定左侧一级导航**
  - 集群概览
  - 节点
  - 目标
  - 事件
  - 设置
- **统一顶部页面头部**
  - 页面标题
  - 一行上下文元信息
  - 搜索槽位
  - 紧凑操作区
- **统一主内容槽位顺序**
  1. 页面摘要条
  2. 当前问题区
  3. 趋势 / 上下文区
  4. 历史 / 事件区
  5. 危险区

新增的 Stitch 壳层基准稿：
- App-Shell Baseline：`projects/11890404311726538701/screens/e5b6094d068546b2bc23603b57c2e46f`

这张稿的作用不是替代所有页面，而是：

> **作为后续 Dashboard、Node Detail、Target Detail、Onboarding 页统一外壳的母版锚点。**

---

### 12.2 语言策略冻结

V1 视觉层采用：

# **中文主界面语言 + 英文技术标识例外**

#### 中文默认覆盖
- 导航
- 页面标题
- 区块标题
- 状态文案
- 操作按钮
- 确认弹层
- 空状态说明

#### 英文仅保留给
- hostname
- 域名
- 技术 ID
- Probe 缩写（TCP / HTTP / TLS）
- 少量不可替代技术术语

这意味着后续开发时，不应再出现：
- 首页中文、详情页英文
- 中文按钮 + 英文面板标题混排
- 普通产品文案英文残留

---

### 12.3 重点层级冻结

后续页面实现时，视觉优先级必须遵守：

1. **当前状态 / 当前问题**
2. **当前摘要与可操作信息**
3. **趋势与上下文**
4. **历史 / 事件**
5. **危险区**

#### 具体落法
- 首页：异常节点区与异常目标区必须同属一等信息
- Node / Target 详情：当前活跃异常优先于趋势图
- Onboarding / Binding Conflict：冲突卡优先于一般状态信息
- 危险区必须明显分离，但不能抢占主问题区的注意力

这条冻结后，后续图表就只能做“辅助理解”，不能重新成为页面主角。

- 中文主界面语言策略
- 当前问题优先于图表的主次规则
