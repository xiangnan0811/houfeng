# 核心页面产品/UX 重新规划

> 日期：2026-05-11
>
> 状态：规划完成，作为下一批前端产品/UX 改造任务的父级依据。
>
> 背景：用户明确认为当前页面“太丑、非常混乱”，不足以支撑真实 VPS 数据测试；因此本阶段先规划核心页面体验，再进入实现。

## 结论

候风下一批前端工作不应继续做真实数据导入，也不应继续机械拆分大文件。当前阻塞点是产品界面本身不能让用户愿意进入真实数据测试。

新的产品/UX 方向是：

```text
候风 = 资产决策工作台 + 观测证据系统

资产决策工作台：VPS、服务商、订阅、续费、成本、迁移/取消决策
观测证据系统：Node、Target、事件、异常、主机指标、探针结果
```

第一批重做的页面应围绕真实 VPS 管理路径组织，而不是围绕后端资源表平铺。

## 当前问题诊断

### 1. 页面不具备真实数据测试吸引力

真实数据测试不是把 JSON 导入数据库后看字段是否存在。用户需要在页面上确认 40+ VPS 是否被正确识别、续费压力是否清晰、哪些机器该保留/迁移/取消，以及资产和观测状态是否能互相解释。

当前页面如果让用户感觉丑、乱、没有操作欲望，真实数据测试会退化成数据库核对，无法验证产品是否真的可用。

### 2. v2 设计语言没有被产品结构承接

`docs/design/v2-houfeng/design-language.md` 已经定义了 dark-first、克制、高密度、工程师长期使用友好的方向。但当前体验仍呈现出：

- 浅色大留白和米白卡片感较强；
- 区块过多，视觉层级依赖卡片边框堆叠；
- 数据表和筛选器比例失衡；
- 首页像多模块概览，而不是一个明确的工作台。

后续实现要把 v2 设计语言落实到页面结构，而不是只调整颜色。

### 3. Asset Ledger 被加进导航，但没有成为主路径

当前导航是扁平列表：

```text
首页 / VPS / 服务商 / 订阅 / 资产决策 / 节点 / 目标 / 事件 / 设置
```

这让 `VPS`、`服务商`、`订阅`、`资产决策` 与 `节点`、`目标`、`事件` 同级并列。用户很难判断：

- 应该先从资产进入，还是先从监控进入；
- 资产决策和 VPS 列表的关系是什么；
- Node/Target/Event 是主功能，还是资产判断的证据。

Asset Ledger 已经是 post-V1 第一条主线，下一批 UX 必须把它提升为真实数据测试入口。

### 4. Dashboard 不是 KPI 墙，也不是 API 字段展板

Dashboard 后续应成为 “Command Desk”，回答一个问题：

> 现在有什么需要我处理？

它不应继续把 fleet 状态、资产摘要、入口、近期事件、各种 summary 平铺成多个同权区块。Dashboard 的主任务应是把资产压力、续费决策、监控异常和下一步动作汇聚起来。

### 5. 列表页需要服务扫描和比较

当前列表页的风险是头部、说明、筛选器比数据更像主体。VPS 列表、资产决策、节点、目标这些页面都应该优先服务：

- 快速扫描；
- 横向比较；
- 找出缺字段、风险、到期、异常；
- 从列表直接进入下一步动作。

筛选器是工具，不是页面主角。高级筛选应更多通过 drawer、chip 或紧凑 control 承载。

### 6. 详情页需要围绕判断和动作组织

VPS 详情页不能只是字段长卷轴。它应该优先回答：

- 这台 VPS 当前应该保留、观察、迁移还是取消；
- 何时续费，成本是多少，自动续费状态如何；
- 它关联了哪些 Node、服务、域名和事件；
- 现在缺什么信息，下一步应该做什么。

Node 详情继续作为观测对象详情；VPS 详情是资产和决策对象详情。二者关联，但不能互相替代。

## 目标体验

### 产品定位

候风的核心页面应像一个长期打开的工程工作台，而不是营销首页或普通 CRUD 后台。

目标感受：

- 冷静、克制、密度高；
- 首屏直接进入工作，不铺陈功能说明；
- 状态色和数字用于判断，不用于装饰；
- 用户能快速知道“今天该处理什么”；
- 资产事实和观测信号互相解释。

### 真实数据测试路径

下一批 UI 应优先支撑这条路径：

1. 进入工作台，看到续费压力、待决策资产、异常资产、缺信息资产。
2. 进入资产决策页，按到期窗口和决策状态处理队列。
3. 进入 VPS 列表，核对 provider、region、price、billing cycle、renewal date、decision、linked node。
4. 进入 VPS 详情，确认单台 VPS 的成本、订阅、决策、服务/域名、关联 Node 和事件时间线。
5. 需要技术证据时，再进入 Node、Target、Event 页面。

### 信息架构方向

后续实现应从扁平导航调整为分组心智模型。具体 UI 形态由实现任务决定，但产品结构应按以下层级理解：

| 分组 | 页面 | 作用 |
|---|---|---|
| 工作台 | 工作台 / Dashboard | 当日处理入口，聚合资产压力与观测异常 |
| 资产 | VPS、资产决策、服务商、订阅 | 真实 VPS 资产管理与续费决策 |
| 观测 | 节点、目标、事件 | 为资产判断提供运行证据 |
| 系统 | 设置 | 主题、通知、账号等系统配置 |

命名建议：

- `首页` 后续可改为 `工作台`。
- `资产决策` 可在导航中表达为 `续费决策` 或保留 `资产决策`，但页面标题必须清楚说明它是工作队列。
- `服务商`、`订阅` 是资产上下文，不应在视觉权重上超过 VPS 和决策队列。

## 核心页面规划

### 1. 工作台 / Dashboard

目标：从概览页变成日常 command surface。

首屏应优先展示：

- `当前需要处理`：到期、未评估、异常、缺字段、自动续费风险。
- `续费窗口`：30 / 60 / 90 天窗口，突出金额和数量。
- `资产健康`：有观测异常的 VPS、失联 Node、服务/域名问题。
- `下一步动作`：进入决策队列、补录资产、处理异常、查看事件。

不要做：

- KPI 墙；
- API 字段展板；
- 大量同权卡片；
- 与 Asset Ledger 无关的普通监控大屏。

验收方向：

- 用户进入首页 5 秒内能判断今天最该处理什么。
- 资产决策入口和 VPS 问题入口比普通管理入口更突出。
- 正常态、空数据态、异常态都不能退回信息堆叠。

### 2. 资产决策页

目标：真实数据测试的主工作队列。

页面应围绕“决策”组织，而不是围绕资产字段展示：

- 按续费窗口、决策状态、金额、provider、linked node health 排序。
- 清楚区分 `未评估`、`保留`、`观察`、`迁移`、`取消`。
- 支持快速查看决策依据：成本、续费时间、用途、关联异常、历史备注。
- 用 drawer 或侧栏承载决策编辑，不打断列表扫描。

验收方向：

- 40+ VPS 数据进入后，用户能一眼看到哪些资产需要优先评估。
- 页面主视觉是队列和判断，不是表单或筛选器。

### 3. VPS 列表页

目标：资产库存总表，服务核对、比较和补录。

建议列优先级：

- VPS 身份：名称、provider、region、IP 或主机提示。
- 成本：价格、币种、计费周期、月化成本。
- 续费：renewal date、auto-renew、剩余天数。
- 决策：当前 renewal decision。
- 观测：linked Node health、最近心跳、活跃异常。
- 数据质量：缺失字段、未关联 Node、缺订阅。

筛选器应紧凑：

- 默认用 quick chips / segmented controls 展示常用视图。
- 高级筛选进 drawer。
- 搜索、provider、到期窗口、决策状态、linked node 状态应优先。

验收方向：

- 列表第一屏显示足够多资产行。
- 筛选器不占据主要视觉注意力。
- 缺失字段和风险资产可直接被发现。

### 4. VPS 详情页

目标：单台 VPS 的资产判断与证据页。

页面结构应优先：

1. 身份与当前决策：名称、provider、region、status、decision、linked node。
2. 续费与成本：价格、周期、续费日期、auto-renew、月化成本、历史变化。
3. 决策依据：用途、备注、风险、experience logs。
4. 关联观测：Node health、事件、目标、主机指标摘要。
5. 服务与域名：VPS-scoped manual service/domain records。
6. 时间线：资产历史、决策历史、体验日志、关键事件。

编辑建议：

- 高频轻编辑放在当前区块内。
- 复杂编辑使用 drawer。
- 危险动作明确隔离。

验收方向：

- 用户能从 VPS Detail 做出“保留 / 观察 / 迁移 / 取消”的判断。
- Node/Target/Event 是证据，不抢占资产主体。

### 5. 节点 / 目标 / 事件

目标：从主产品中心降级为观测证据系统，但保留专业性。

节点页：

- 优先呈现 linked VPS 上下文。
- 异常和 freshness 仍然重要，但应帮助资产判断。
- 列表密度和筛选器权重需要收敛。

目标页：

- 作为服务/入口观测列表。
- 后续可与 VPS-scoped services 形成入口关系，但不做完整服务注册表。

事件页：

- 作为审计与诊断时间线。
- 支持从 Dashboard、VPS Detail、Node Detail 深链进入。
- 默认视图应清楚显示对象、严重度、时间和关联资产。

## 视觉与交互原则

### Dark-first 不是可选装饰

后续核心页面默认应回到 dark-first 工程工具方向。Light 主题仍要可用，但不能让页面设计被浅色大留白主导。

### 高密度但不拥挤

密度应来自：

- 表格行高和列信息层次；
- 紧凑状态条；
- inline metadata；
- drawer 承载二级操作；
- 状态 glyph、badge、mono 数字帮助扫描。

密度不应来自：

- 过多卡片；
- 卡片套卡片；
- 大段说明文本；
- 复杂装饰背景；
- 首屏多个同权大模块。

### 页面控件服务工作流

- 按钮只用于明确动作。
- 链接用于导航。
- 图标按钮需要 tooltip 或清晰 aria label。
- 数字使用 tabular mono。
- 长 hostname、ID、摘要必须截断或换行，不破坏布局。
- 空态要引导下一步，不展示大面积空容器。

## 后续实现批次

### UX-1：App shell / 导航 / 视觉基线重置

范围：

- 调整导航心智模型，至少在视觉上形成工作台、资产、观测、系统分组。
- 将 `首页` 方向收敛为 `工作台`。
- 统一页面 chrome、主区域密度、浅色/暗色主题默认体验。
- 减少无意义 page panel / card chrome。

非目标：

- 不改后端模型。
- 不重做所有页面业务逻辑。
- 不引入 CSS 框架或 UI 库。

### UX-2：Dashboard 工作台重塑

范围：

- 把 Dashboard 改为资产决策 + 观测异常 command surface。
- 重新组织 asset summary、renewal windows、异常对象、缺信息资产和下一步动作。
- 保留必要深链到 VPS、资产决策、节点、目标、事件。

非目标：

- 不新增复杂评分算法。
- 不把所有 API 字段展示出来。

### UX-3：资产决策 + VPS 列表重塑

范围：

- 资产决策页变成工作队列。
- VPS 列表变成高密度资产库存表。
- 筛选器收敛为 quick views + chips + drawer。
- 支撑真实 40+ VPS 数据人工核对。

非目标：

- 不运行真实数据 import。
- 不做 Provider/DNS 自动同步。

### UX-4：VPS 详情页重塑

范围：

- 重排 VPS Detail：身份、决策、续费/成本、观测证据、服务/域名、时间线。
- 强化关联 Node 和事件作为证据。
- 通过 drawer/section 收敛复杂编辑。

非目标：

- 不做完整服务注册表。
- 不做完整域名管理或 DNS record 管理。

### UX-5：观测支撑页收敛

范围：

- 收敛 Nodes / Targets / Events 的列表密度、筛选权重和资产上下文。
- 保留现有观测能力和 URL-state 深链。
- 补齐与 VPS 详情、Dashboard 的跨页关系。

非目标：

- 不重写观测系统数据模型。
- 不做大屏监控中心。

### UX-6：视觉证据与验收流程

范围：

- 为核心页面建立可复核截图或本地预览流程。当前 active 流程见 `docs/operations/v2-visual-evidence.md`。
- 实现任务完成时必须启动 dev server，并给出预览 URL、检查路由和视口。
- 需要时补充本地浏览器 sanity、截图或轻量视觉证据；不把临时 Playwright/浏览器工具变成 repo 依赖。

非目标：

- release/publish workflow 暂不处理。

## 暂不处理

- 真实 40+ VPS 数据 dry-run/import。
- 前端大文件机械拆分。
- Provider/DNS 同步。
- Web SSH。
- 插件系统。
- 服务发现或完整服务注册表。
- 完整域名管理、Registrar 同步、DNS record 管理。
- 多用户 RBAC。
- 汇率换算、多币种归一化。
- 复杂评分算法。
- release/publish workflow。
