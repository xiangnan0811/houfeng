## v1 一句话定位

这是一个：

> **面向个人多服务器舰队的异常发现与观测控制面**

而不是：

- 通用运维平台
- Docker 编排平台
- 完整资产台账 / CMDB
- 任意脚本执行系统
- 多租户监控平台

## v1 冻结边界（当前结论）

### 系统形态

- 单用户个人系统
- `1 个单体中心控制面 + 1 个 PostgreSQL + N 个 systemd agent`
- agent 主动访问中心，中心不回连 agent

### Agent 定位

- 常驻 systemd 二进制
- 宿主机视角采集
- 薄 agent，不做万能执行器
- 负责：
  - 注册 / 身份识别
  - 心跳
  - 主机指标采集
  - 执行有限探针
  - 上报结果
  - 拉取配置
  - 短期持久化缓冲
- 不负责：
  - 任意脚本执行
  - Docker 编排
  - 复杂规则引擎
  - 本地长期存储

### 监控范围

- 主机基础指标
- 少量宿主机诊断信号
  - `iowait`
  - `steal`
  - swap
  - 磁盘读写 / 忙碌度简化指标
- 探针类型仅限：
  - TCP
  - HTTP/HTTPS
  - TLS

### 观测对象模型

- `Node = 一台具体服务器`
- `Target = 一个明确的可观测入口`
- `ProbeItem = 挂在 Target 下的具体观测方式`
- `HostSample / ProbeObservation = 原始事实记录`

### 目标范围

- 你的自建服务入口
- 一小组固定国内参考目标

### 执行范围

- 按 **节点标签** 分配探针执行范围
- 执行范围挂在 `Target` 上
- 同一 `Target` 下的所有 `ProbeItem` 默认由同一组节点执行

### 首页结构

- 当前异常节点摘要
- 当前异常目标摘要
- 最近异常事件流

### 健康状态

`Node` / `Target` 都采用：

- 正常
- 关注
- 告警
- 严重

### 通知

- 最小通知能力
- 仅 Telegram
- 只通知值得打断人的变化：
  - 异常开始
  - 状态升级
  - 异常恢复

### 数据策略

- 原始观测先入库
- 单体内部后台再做：
  - 异常判定
  - 去抖
  - 健康状态归并
  - 通知决策
- 数据采用分层保留：
  - 原始层：短中期保留
  - 聚合层：长期保留
  - 事件 / 通知层：长期保留

## 当前最重要的设计原则

1. **配置面明显轻于观测面**
2. **状态切换与结构编辑分开**
3. **统一规则集中在中心，不下放到 agent**
4. **能用状态表达的，不优先用删除**
5. **先做小而稳的 v1，不为了未来预埋一整个通用平台**
