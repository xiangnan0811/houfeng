# 服务器舰队控制面 v1 详细设计：异常、交互与默认规则

> 相关：[[服务器舰队控制面-v1-设计总览]]、[[服务器舰队控制面-v1-详细设计-架构、数据与模型]]

## 1. 异常体系

v1 只保留 3 大类异常：

### 1.1 资源压力异常

面向 `Node`，关注机器本身是否进入高压或危险区间。

典型来源：

- CPU 使用率过高
- load 持续过高
- 内存压力过高
- swap 使用明显升高
- 磁盘空间不足
- inode 紧张
- `iowait` 持续偏高
- `steal` 持续偏高
- 磁盘忙碌度 / 等待信号持续异常

### 1.2 探针异常

面向 `Target`，关注入口可用性或连通性问题。

典型来源：

- TCP 失败
- HTTP/HTTPS 失败
- HTTP 状态码不符合预期
- TLS 建立失败
- TLS 证书进入危险阈值

### 1.3 趋势退化异常

面向 `Node` / `Target`，关注“没有完全坏掉，但正在持续变差”的情况。

典型来源：

- 到国内参考目标 latency 持续升高
- `steal` / `iowait` 逐步恶化
- 某入口最近明显慢于自身近期基线

## 2. 健康状态归并

`Node` / `Target` 都采用：

- 正常
- 关注
- 告警
- 严重

### 2.1 健康状态与异常的关系

- 异常是“问题项”
- 健康状态是“当前整体局面的摘要”

### 2.2 归并原则

1. **最严重异常优先**
2. **多个低级异常可叠加升级**
3. **趋势退化默认权重低于硬故障**
4. **维护模式覆盖健康状态更新**

## 3. 去抖与确认模式

v1 采用 3 种确认模式：

### 3.1 快速触发类

适用于：

- 节点离线 / 心跳丢失
- 磁盘空间接近耗尽
- inode 接近耗尽
- TLS 证书进入非常危险区间

### 3.2 连续失败类

适用于：

- TCP 连续失败
- HTTP 连续失败
- TLS 连续失败

### 3.3 持续确认类

适用于：

- CPU 持续高
- load 持续高
- `steal` 持续升高
- `iowait` 持续升高
- latency 持续高于近期基线

## 4. 规则策略

v1 采用：

> **全局默认规则 + 少量按标签/类型覆盖**

### 4.1 覆盖维度

- 节点标签
- Target 类型
- Target 标签

### 4.2 明确不做

- 每个对象完全自由配置规则
- 任意表达式规则语言
- 通用规则平台

## 5. Telegram 通知语义

v1 只接入 Telegram，并且：

> **只通知值得打断人的变化**

### 5.1 应通知的场景

- 异常开始
- 状态升级
- 异常恢复

### 5.2 不应通知的场景

- 每个 observation
- 每次单点超阈值
- 每次单次探针失败
- 补传的历史老异常
- 维护期间的采样结果

### 5.3 降噪原则

1. 同一活跃异常只发一次开始通知
2. 只有升级时再次发
3. 恢复单独发一次
4. 维护期间完全静默
5. 补传历史默认不触发追溯通知

例如：

- Node → 已退役

- ProbeItem → 停用

删除更适合“误建对象”，不是常规管理动作。

## 8. 默认频率档位与默认规则草案

这一节是当前新增的设计收敛，重点回答：

> v1 到底该预置哪些频率档位，以及默认规则应该保守到什么程度。

## 8.1 频率档位原则

我们已经冻结：

- 频率不全局固定
- 也不允许完全自由输入
- 采用**少量预置档位**

### 设计原则

1. 档位应该足够少，避免配置碎片化
2. 档位名称最好同时有“语义名 + 明确时间”
3. 主机指标、TCP/HTTP/TLS 都从同一套档位里选
4. 不同对象默认档位可不同，但档位集合本身统一

## 8.2 推荐的 v1 频率档位

我建议 v1 只保留这 4 档：

- `1m`（fast）
- `5m`（normal）
- `15m`（slow）
- `6h`（rare）

### 为什么是这 4 档

#### `1m`
用于：
- 核心服务入口
- 高价值 TCP / HTTP 探针
- 关键 Node 的主机指标

#### `5m`
用于：
- 大多数普通服务探针
- 大多数 Node 的基础采样

#### `15m`
用于：
- 低优先级目标
- 观察中节点
- 数据量更敏感的场景

#### `6h`
用于：
- TLS 证书类检查
- 极低频参考项

### 为什么不建议更多

因为：

- 2m / 3m / 10m / 30m 这类档位很快会让系统变碎
- v1 的重点不是“精确到每个对象都能调出最完美频率”
- 而是“足够用，而且整体可控”

## 8.3 推荐的默认采样节奏（v1 建议）

> 这里仍然是设计建议，不是实施定值；重点是给出推荐默认语义。

### Node 主机指标

默认建议：`5m`

原因：
- 对大多数 VPS 足够
- 数据量适中
- 能看出长期压力与退化

### 关键 Node（如 `核心` 标签）

默认建议可覆盖为：`1m`

### 普通 service 类型 Target

默认建议：
- HTTP：`5m`
- TCP：`5m`
- TLS：`6h`

### 核心 service / 高优先级入口

默认建议可覆盖为：
- HTTP：`1m`
- TCP：`1m`
- TLS：`6h`

### china_reference 类型 Target

默认建议：
- TCP：`5m`

### 为什么国内参考目标不默认 1m

因为你的重点是看“持续退化”，不是做秒级 SLA 系统。  
`5m` 对 v1 更稳、更省资源，也足以看线路趋势。

## 8.4 资源压力异常：默认规则草案

这里不写死最终数值，只定义**推荐的设计方向**。

### CPU / load

- 单次尖峰不成立异常
- 采用**持续确认**
- 先进入 `关注`
- 长时间持续再升级到 `告警`
- 除非叠加其他问题，否则不应轻易直接推到 `严重`

### 磁盘空间

- 采用**较快触发**
- 因为它更接近硬边界风险
- 可设计两级阈值：
  - 高位进入 `关注`
  - 接近耗尽进入 `严重`

### inode

- 语义与磁盘空间类似
- 接近耗尽应视为高风险

### swap / 内存压力

- 适合做**持续确认**
- 不能仅靠一瞬间 swap 有值就异常

### `iowait` / `steal`

- 默认作为**趋势退化 / 资源压力辅助信号**
- 更适合推到 `关注`
- 在和其他压力信号叠加时，再提升到 `告警`

## 8.5 探针异常：默认规则草案

### TCP

- 采用**连续失败确认**
- 不因一次超时立刻成立异常
- 连续失败达到阈值后进入 `告警`
- 长时间连续失败或多节点持续失败可升级 `严重`

### HTTP

- 采用**连续失败确认**
- 5xx、timeout、连接错误都可计入失败语义
- expected status 不命中也计入失败
- 恢复也应要求一定的连续成功，避免抖动

### TLS

- 建立失败：按连续失败类处理
- 证书到期：按阈值窗口处理
  - 进入预警窗口：`关注`
  - 进入危险窗口：`告警`
  - 已过期或极短窗口：`严重`

## 8.6 趋势退化异常：默认规则草案

趋势退化是 v1 里最应该保守设计的一类异常。

### 设计原则

1. 默认慢半拍
2. 默认不直接推严重
3. 必须基于时间窗口或近期基线
4. 更适合作为“关注”或“告警”的来源

### Node 趋势退化

可观察：
- latency 整体变高
- `steal`、`iowait` 持续恶化
- load 长期偏高

### Target 趋势退化

可观察：
- TCP connect latency 持续高于近期基线
- 多执行节点视角一致变差
- 但尚未真正失败

## 8.7 默认规则与覆盖的推荐落法

### 全局默认

提供一套适用于绝大多数对象的：

- 主机资源异常规则
- 探针失败规则
- 趋势退化规则

### 节点标签覆盖

适用于：
- `核心`
- `低配`
- `观察中`

### Target 类型 / 标签覆盖

适用于：
- `service`
- `china_reference`
- `高优先级`

## 8.8 v1 默认规则设计应避免的坑

### 1）不要让“观察中”天然更容易报警

观察中是管理语义，不一定意味着更敏感或更宽容。  
是否覆盖，应由你明确设定。

### 2）不要把趋势退化做得比硬故障更吵

否则你会迅速厌烦这个系统。

### 3）不要为了少数特殊对象引入每对象自由规则

v1 必须坚持：

- 默认规则
- 少量覆盖
- 不做无限自由

## 8.9 这一节的结论

如果把这一节冻结，v1 的默认行为可以总结为：

- 频率采用 **4 档预置**
  - `1m / 5m / 15m / 6h`
- 主机指标默认 `5m`
- 普通 service 探针默认 `5m`
- TLS 默认 `6h`
- china_reference 默认 `5m`
- 资源压力异常偏保守，但磁盘 / inode 可更快触发
- 探针异常走连续失败确认
- 趋势退化默认最保守
- 全局默认 + 少量按标签 / 类型覆盖

这很符合 v1 的总体方向：

> **不追求把系统调得极度花哨，而是先确保默认行为就已经足够靠谱。**

## 9. 默认阈值、确认窗口与状态升级草案

这一节对应设计过程中的**第 8 节**，重点不是把每一个数字永久钉死，而是先给出一版：

> **足够保守、可长期运行、适合低配异构 VPS 舰队的默认阈值草案**

这些默认值的目标是：

- 先可用
- 先不吵
- 先能发现明确问题
- 先能把“正在退化”和“已经坏了”区分开

---

### 9.1 阈值设计总原则

#### 原则 1：硬边界问题优先

像：

- 节点离线
- 磁盘空间快耗尽
- inode 快耗尽
- 入口持续不可达

这类应该比：

- CPU 偶发高
- latency 小幅抬升
- 轻微 `steal`

更快进入高等级状态。

#### 原则 2：瞬时尖峰默认不算异常

v1 不应把一次偶发抖动解释成值得通知的问题。  
所以大多数资源压力类指标都应该：

- 先观察窗口
- 再确认成立

#### 原则 3：趋势退化默认保守

趋势异常的使命是：

> 提醒你“值得继续观察”

而不是：

> 把系统变成对每一次小波动都过度敏感的噪音源。

#### 原则 4：升级比开始更谨慎

一个对象从 `关注 -> 告警 -> 严重` 的升级，  
应该随着等级升高，确认条件更苛刻，而不是更随意。

---

### 9.2 Node 资源压力类默认阈值草案

> 下面这组阈值是 **v1 初始建议值**，不是永久真理。  
> 真正上线时应允许你按标签做少量覆盖，但不建议偏离太多。

#### CPU 使用率

- **关注**：连续 `15m` 平均 >= `80%`
- **告警**：连续 `15m` 平均 >= `90%`
- **严重**：连续 `30m` 平均 >= `95%`

##### 设计理由

- CPU 很容易出现短时峰值
- 用 `15m` 窗口可以过滤很多无意义尖峰
- 只有高位持续占用，才说明机器真的长期吃紧

#### Load

我建议不要用固定绝对值，而是按 **CPU 核心数归一化理解**。  
也就是更接近：

> `load1 / cpu_cores`、`load5 / cpu_cores`

##### 初始建议

- **关注**：连续 `15m`，归一化 load >= `1.2`
- **告警**：连续 `15m`，归一化 load >= `1.8`
- **严重**：连续 `30m`，归一化 load >= `2.5`

##### 设计理由

- 你的节点异构明显，1C / 2C / 4C / 10C 差异很大
- 不归一化的话，固定阈值会非常不合理

#### 内存使用率 / 可用内存

建议主看：

- `mem_used_pct`
- `mem_available_bytes`

##### 初始建议

- **关注**：连续 `15m` 内存使用率 >= `85%`
- **告警**：连续 `15m` 内存使用率 >= `92%`
- **严重**：连续 `30m` 内存使用率 >= `95%`，且可用内存维持在很低水平

##### 设计理由

- 内存本身也会抖动
- 单次高水位不一定意味着危险
- 要看持续性

#### Swap 使用

swap 我建议默认不单独拉升到严重，除非叠加其他信号。

##### 初始建议

- **关注**：连续 `15m` swap 使用率明显高于平时基线，或持续 > `10%`
- **告警**：连续 `30m` swap 使用率持续高位，且伴随 CPU/load/内存压力

##### 设计理由

- 某些机器有少量 swap 使用并不一定是坏事
- swap 更适合作为“系统压力辅助信号”

#### 磁盘空间

##### 初始建议

- **关注**：磁盘使用率 >= `85%`
- **告警**：磁盘使用率 >= `92%`
- **严重**：磁盘使用率 >= `97%`

##### 设计理由

- 这是典型的硬边界问题
- 不应像 CPU 那样过度依赖长窗口
- 可以有很短确认窗口，但应快速成立

#### inode 使用率

##### 初始建议

- **关注**：inode 使用率 >= `80%`
- **告警**：inode 使用率 >= `90%`
- **严重**：inode 使用率 >= `95%`

##### 设计理由

- inode 打满的破坏性常常不亚于磁盘打满
- 但很多人容易忽略，所以默认应更敏感一点

#### `iowait`

##### 初始建议

- **关注**：连续 `15m` 平均 >= `10%`
- **告警**：连续 `30m` 平均 >= `20%`

##### 设计理由

- 对 VPS 来说，`iowait` 偏高很值得看
- 但单独依靠它，不建议直接进入 `严重`

#### `steal`

##### 初始建议

- **关注**：连续 `15m` 平均 >= `5%`
- **告警**：连续 `30m` 平均 >= `10%`

##### 设计理由

- `steal` 对你判断“是否像被超售影响”非常有价值
- 但它天然更适合趋势与观察，不适合直接做最重级别

---

### 9.3 Node 离线默认规则草案

#### 初始建议

- **关注**：最近 `2` 个心跳周期未收到
- **告警**：最近 `3` 个心跳周期未收到
- **严重**：最近 `5` 个心跳周期未收到

> 具体数值最终仍要和心跳频率绑定，但设计语义是：
> **离线问题要比 CPU、load 等压力问题更快抬级。**

##### 设计理由

- 节点离线对整个观测体系影响大
- 这是最典型的“快速触发类”

---

### 9.4 Target 探针失败默认规则草案

#### TCP

##### 初始建议

- **关注**：连续 `2` 次失败
- **告警**：连续 `3` 次失败
- **严重**：连续 `6` 次失败，或在多个执行节点上同时持续失败

#### HTTP

##### 初始建议

- **关注**：连续 `2` 次失败
- **告警**：连续 `3` 次失败
- **严重**：连续 `5` 次失败，或同目标多个 ProbeItem 同时异常

#### TLS 建立失败

##### 初始建议

- **关注**：连续 `2` 次失败
- **告警**：连续 `3` 次失败
- **严重**：连续 `5` 次失败

##### 设计理由

- 一次失败太容易抖
- 3 次左右通常足够把“真实异常”和“偶发抖动”区分开
- 严重状态需要更强确认，避免系统过于吵闹

---

### 9.5 TLS 证书到期默认规则草案

TLS 到期更像“时间窗口型风险”，不属于连续失败类。

#### 初始建议

- **关注**：证书剩余 <= `30` 天
- **告警**：证书剩余 <= `14` 天
- **严重**：证书剩余 <= `3` 天，或证书已过期

##### 设计理由

- 30 天足够你提前看到风险
- 14 天开始值得进入处理队列
- 3 天以内应该被视为明显高风险

---

### 9.6 趋势退化默认规则草案

这是 v1 最需要保守设计的部分。

#### Node 趋势退化

可用于：

- `steal`
- `iowait`
- 到国内参考目标的 latency 汇总表现
- load / 资源压力长期高于自身近期基线

##### 初始建议

- **关注**：在 `24h` 窗口内，明显高于自身近 `7d` 近期基线
- **告警**：在 `24h` 窗口内，持续明显偏离，且伴随其他压力信号
- 默认不直接推 `严重`

#### Target 趋势退化

适用于：

- `china_reference`
- service 入口 latency 持续升高但尚未失败

##### 初始建议

- **关注**：`24h` 内明显高于该目标近期基线
- **告警**：多个执行节点视角一致持续变差
- 默认不直接推 `严重`

##### 设计理由

- 趋势退化的作用是提前发现“变差”
- 不是替代硬故障检测
- 所以它应天然更保守

---

### 9.7 恢复规则草案

异常不应该一恢复一个点就立刻解除。

#### 资源压力异常恢复

建议：

- 至少要求连续一个确认窗口恢复到安全区间以下

#### 探针失败恢复

建议：

- TCP / HTTP / TLS 默认要求连续 `2` 次成功后恢复

#### 趋势退化恢复

建议：

- 需要在一个更长窗口里回落到接近基线
- 不应因为一次短时改善立刻恢复

##### 设计理由

- 恢复也要去抖
- 不然状态会频繁来回抖动，Telegram 也会跟着很烦

---

### 9.8 状态升级建议草案

这里我建议 v1 明确采用：

> **升级比开始更谨慎，恢复也比单次成功更保守**

#### 推荐升级语义

- `正常 -> 关注`：较容易成立
- `关注 -> 告警`：要求持续性或叠加性
- `告警 -> 严重`：要求硬边界或强确认

#### 推荐叠加升级逻辑

例如 Node：

- 一个轻度磁盘问题 → `关注`
- 一个轻度磁盘问题 + 一个持续高 load 问题 → 可升级 `告警`
- 磁盘接近耗尽 / 节点离线 → 可直接 `严重`

例如 Target：

- 单个 HTTP 探针连续失败 → `告警`
- HTTP + TCP 同时失败 → `严重`
- 多执行节点同时失败 → 更容易升级 `严重`

---

### 9.9 标签 / 类型覆盖建议草案

这里我建议 v1 只支持少量有强业务价值的覆盖。

#### 节点标签覆盖建议

##### `核心`

- 可适当更敏感
- 更容易从 `关注` 升到 `告警`

##### `低配`

- 可对 CPU / 内存轻度波动略宽容
- 但对磁盘 / inode 不应放宽

##### `观察中`

- 不建议默认更敏感
- 是否覆盖由你明确决定

#### Target 类型覆盖建议

##### `service`

- 更重视可用性失败

##### `china_reference`

- 更重视 latency 退化趋势
- 但默认仍应保守

---

### 9.10 v1 默认阈值设计应避免的坑

#### 1）不要把每个指标都做成 3 档齐全且完全独立

有些信号更适合：

- 只做关注 / 告警
- 或只做告警 / 严重

不需要所有字段都强行对齐成完全一样的升级结构。

#### 2）不要让趋势退化盖过硬故障

硬故障应该更强、更直接。  
趋势退化是辅助你做长期判断，不是抢首页头条。

#### 3）不要对所有节点一视同仁地追求“灵敏”

异构舰队的现实就是：

- 有核心节点
- 有低配鸡场
- 有观察中节点

所以少量覆盖是必要的，但必须保持克制。

---

### 9.11 这一节的结论

如果把这一节冻结，v1 的默认行为会进一步明确为：

- CPU / load / 内存类问题：**持续确认**
- 磁盘 / inode / 离线类问题：**更快触发**
- TCP / HTTP / TLS 失败：**连续失败确认**
- TLS 到期：**时间窗口型预警**
- 趋势退化：**默认最保守**
- 升级比开始更谨慎
- 恢复也需要去抖

换句话说，v1 的默认规则哲学是：

> **先把“明确的问题”抓稳，再把“正在变差”的信号做保守提醒。**
