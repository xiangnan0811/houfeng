# 服务器舰队控制面 v1 详细设计：交互原型与操作流

> 相关：[[服务器舰队控制面-v1-设计总览]]、[[服务器舰队控制面-v1-详细设计-架构、数据与模型]]、[[服务器舰队控制面-v1-详细设计-异常、交互与默认规则]]、[[服务器舰队控制面-v1-审阅清单与待决问题]]

这份文档对应当前设计过程中的：

> **设计第 11 节：Node / Target / ProbeItem 的创建、编辑、状态切换交互原型草案**

它的目标不是设计视觉稿，而是把：

- 高频创建流程
- 高频状态切换
- 危险操作确认
- 绑定冲突处理
- 空状态与引导路径

收敛成一套**可评审、可继续调整的交互骨架**。

---

## 1. 交互设计总原则

### 1.1 观测优先，配置次之

系统的主体验应该是：

- 先看状态
- 再看异常
- 再进入详情
- 最后才是编辑配置

因此配置入口不应该在信息层级上压过观测入口。

### 1.2 结构编辑与运行控制分离

这是 v1 很重要的一条原则。

#### 结构编辑

例如：

- 改名称
- 改地区 / 城市 / 供应商
- 改 host / base_port
- 改标签
- 改 ProbeItem 参数

这类操作应通过：

- 编辑按钮
- 侧边抽屉 / 结构表单

来完成。

#### 运行控制

例如：

- 进入维护模式
- 暂停监控
- 恢复监控
- 归档
- 退役
- 重置绑定

这类操作应通过：

- 状态按钮
- 快捷动作
- 明确确认弹层

来完成。

不能把这两类操作都塞进一个“编辑对象”入口里。

### 1.3 高频动作就地完成

对高频动作，默认原则是：

- 在列表里能做的，不强迫进详情
- 在详情头部能做的，不埋进底部表单
- 需要天天看、经常点的动作，不要藏在设置里

### 1.4 危险动作强确认，可逆动作轻确认

#### 轻确认 / 快捷切换

适用于：

- 进入维护模式
- 退出维护模式
- 恢复监控

#### 强确认

适用于：

- 暂停监控
- 归档 Target
- 节点退役
- 重置绑定
- 删除对象

---

## 2. 顶层导航的交互语义

v1 顶层导航固定为：

- 首页
- 节点
- 目标
- 事件
- 设置

### 为什么这里不再扩展

不单独拆出：

- 规则中心
- 探针中心
- 通知中心
- 维护中心
- 资产中心

是为了避免系统一开始就显得像一个企业后台。

这些能力应该：

- 依附在对象上
- 或依附在设置页

而不是单独长成一个新模块。

---

## 3. Node 创建与接入原型

### 3.1 入口位置

建议保留两个入口：

1. 节点列表页主按钮：`新建节点`
2. 首页异常节点区域为空时的 CTA：`创建第一个节点`

### 3.2 Node 创建表单原型

建议采用：

> **短表单 + 右侧抽屉 / 轻模态**

而不是多步骤 wizard。

#### 字段

##### 必填

- 显示名称
- 地区
- 城市
- 供应商
- 生命周期状态（默认 `待接入`）

##### 可选

- 标签
- 备注

##### 不进入创建第一步的字段

- IP
- 套餐
- 价格
- 到期时间
- 带宽
- 跑分

### 3.3 Node 创建后的落点

创建成功后，不建议回到列表页，而是进入：

# **节点接入准备页**

#### 这页应至少包含

##### A. 节点身份卡

- 显示名称
- 地区 / 城市
- 供应商
- 生命周期状态
- 监控运行状态
- 当前绑定状态

##### B. Token 区域

- 专属 token 的受控显示
- 复制操作
- 再生成 / 重置入口（高风险）

##### C. 接入说明区域

- agent 安装与接入步骤
- 当前配置版本摘要

##### D. 状态反馈区域

- 最近一次接入尝试状态
- 最近一次失败原因摘要（如有）
- 当前是否已有机器指纹

##### E. 后续动作

- 查看节点详情
- 返回节点列表

### 3.4 Node 列表页交互原型

#### 每行信息建议

- 显示名称
- 地区 / 城市
- 供应商
- 生命周期状态
- 监控运行状态
- 健康状态
- 活跃异常数
- 最近一次上报时间
- 标签摘要
- 当前关键异常摘要

#### 每行快捷动作建议

- 进入维护 / 退出维护
- 暂停 / 恢复监控
- 编辑标签
- 查看详情

#### 不建议放在列表行的动作

- 重置绑定
- 修改生命周期状态
- 删除
- 编辑所有字段

### 3.5 Node 详情页交互原型

#### 头部区域建议展示

- 显示名称
- 地区 / 城市
- 供应商
- 标签
- 生命周期状态
- 监控运行状态
- 当前健康状态
- 最近一次心跳 / 同步
- 当前主问题摘要

#### 头部高频动作建议

##### 运行控制

- 进入维护
- 退出维护
- 暂停监控
- 恢复监控

##### 管理动作

- 编辑基本信息
- 编辑标签
- 修改生命周期状态
- 重置绑定

### 3.6 Node 绑定冲突处理原型

#### 触发场景

- token 正确
- 但机器指纹与当前绑定不一致

则 Node 进入：

- `指纹变更待确认`

#### 页面表现建议

##### 列表页

- 该节点出现明显的身份异常标记
- 可被“绑定异常”筛选出来

##### Node 详情页

在显著区域出现：

# **绑定冲突横幅 / 冲突处理卡片**

并提供：

- 确认重绑定
- 拒绝新指纹
- 重置绑定

## 4. Target 创建与管理原型

### 4.1 入口位置

建议保留两个入口：

1. 目标列表页主按钮：`新建目标`
2. 目标列表空状态 CTA：`创建第一个目标`

### 4.2 Target 创建表单原型

建议采用：

> **短表单 + 创建后继续补 ProbeItem**

#### 必填

- 名称
- 类型（`service` / `china_reference`）
- `host`
- 执行节点标签
- 运行状态

#### 可选

- `base_port`
- 标签
- 备注

### 4.3 Target 创建后的落点

Target 创建成功后，直接进入：

# **Target 详情页**

并在 ProbeItem 区域展示明显空状态：

> 当前还没有 ProbeItem，请为该入口添加至少一种观测方式。

### 4.4 Target 列表页交互原型

#### 每行信息建议

- 名称
- 类型
- host / base_port
- 标签
- 运行状态
- 当前健康状态
- ProbeItem 数量
- 异常 ProbeItem 数量
- 最近一次成功观测时间
- 关键异常摘要

#### 每行快捷动作建议

- 进入维护 / 退出维护
- 暂停 / 恢复
- 归档
- 编辑标签
- 查看详情

### 4.5 Target 详情页交互原型

#### 头部区域建议展示

- 名称
- 类型
- host / base_port
- 标签
- 执行节点标签
- 运行状态
- 健康状态
- 当前主要异常摘要

#### 头部高频动作建议

- 进入维护 / 退出维护
- 暂停 / 恢复
- 归档
- 编辑基本信息
- 编辑标签

#### 详情页主体最重要区域

# **ProbeItem 列表**

因为 Target 的观测能力都挂在这里。

---

## 5. ProbeItem 创建与编辑原型

### 5.1 创建入口

ProbeItem 只建议从以下位置创建：

- Target 详情页
- Target 创建后的空状态 CTA

### 5.2 创建方式

建议采用：

> **先选类型，再打开对应短表单**

#### TCP

- 端口（默认可带入 `base_port`）
- timeout
- 频率档位
- 启用状态

#### HTTP

- scheme
- path
- method（仅 GET / HEAD）
- expected status 范围
- timeout
- 频率档位
- 启用状态

#### TLS

- 端口（默认可带入 `base_port`）
- timeout
- 频率档位
- 证书阈值
- 启用状态

### 5.3 ProbeItem 编辑与启停

建议只保留：

- 编辑
- 启用
- 停用
- 删除（仅误建）

不再额外赋予 ProbeItem 复杂运行状态。

---

## 6. 状态切换的交互语义

### 6.1 轻量运行控制动作

适用于：

- 进入维护
- 退出维护
- 恢复监控 / 恢复目标

建议：

- 列表页和详情页头部都可操作
- 尽量一键完成
- 不做重表单

### 6.2 中等风险动作

适用于：

- 暂停 Node 监控
- 暂停 Target

建议：

- 需要明确确认
- 但不必进入危险红区

### 6.3 高风险动作

适用于：

- Node 退役
- Target 归档
- 重置绑定
- 删除对象

建议：

- 必须二次确认
- 尽量在详情页内操作
- 在 UI 上和普通操作明显区隔

---

## 7. 标签编辑原型

### 7.1 列表页中的快速标签编辑

适合：

- 快速补标签
- 小范围修正

建议：

- 用轻量弹出层
- 不进入完整编辑页

### 7.2 详情页中的完整标签编辑

适合：

- 一次性整理多个标签
- 连同备注一起调整

### 7.3 为什么不做独立标签中心

因为 v1 的标签仍然只是对象的辅助管理语义，  
还没有必要长成独立产品域。

---

## 8. 删除、归档、退役的区分

### 删除

适用语义：

> 这个对象建错了

不是日常管理手段。

### 归档（仅 Target）

适用语义：

> 这个目标不再活跃，但历史必须保留

### 退役（仅 Node 生命周期）

适用语义：

> 这台机器退出活跃舰队，但 Node 历史仍保留

---

## 9. 空状态与引导路径原型

### 9.1 首页空状态

当还没有 Node / Target 时，应清楚引导：

1. 先创建 Node
2. 接入 agent
3. 再创建 Target
4. 再添加 ProbeItem

### 9.2 Node 接入前空状态

Node 创建后但还未绑定时：

- 显示明显的接入准备卡
- 而不是普通详情页的空图表

### 9.3 Target 无 ProbeItem 空状态

Target 创建后没有 ProbeItem 时：

- 明确提示入口已存在
- 但还未配置观测方式

并提供：

- 新增 TCP
- 新增 HTTP
- 新增 TLS

三个清晰入口

---

## 10. 这一节的结论

如果把这一节冻结，v1 的交互原型可以浓缩成一句话：

# **创建要短、状态切换要快、危险动作要重确认、空状态要有清楚引导。**

更具体一点：

- Node 创建后进入 **接入准备页**
- Target 创建后进入 **详情页 + ProbeItem 空状态**
- ProbeItem 只在 Target 内创建
- 运行控制动作与结构编辑动作彻底分开
- 高风险动作必须在详情页或红区完成
- 列表页只保留高频且低摩擦的动作

这套交互原型的核心价值是：

> **让系统先成为“好用的个人工具”，而不是一个看起来很全、实际很重的平台后台。**

## 11. 状态化页面与关键确认流草案

这一节对应当前设计过程中的：

> **设计第 11 节：接入准备页、绑定冲突页、维护模式与归档确认的状态化页面草案**

它的目标是把最有“运行语义”的几个页面/弹层进一步收紧：

- 接入准备页
- 绑定冲突处理页
- 维护模式开启/结束确认
- Target 归档确认
- Node 退役确认
- 暂停监控确认

这些页面的共同特点是：

- 不是普通编辑表单
- 承担明确的系统状态切换语义
- 一旦设计不清，后面很容易出错或让用户心智混乱

---

### 11.1 状态化页面的设计原则

#### 原则 1：明确回答“为什么现在会看到这个页面/弹层”

这些页面不能只是“让你点确认”。  
它们必须先解释：

- 当前状态是什么
- 为什么需要你介入
- 这次动作会改变什么
- 哪些东西不会被改变

#### 原则 2：必须告诉用户“这次动作影响的是哪一层状态”

例如：

- 是生命周期状态变了
- 还是监控运行状态变了
- 还是绑定关系变了
- 还是只是通知被静默了

如果这一层不讲清楚，后面就会经常出现“我以为暂停等于归档”“我以为维护等于停采集”之类的误解。

#### 原则 3：先展示当前状态，再展示目标状态

这些确认页/弹层都应该尽量用：

- 当前：xxx
- 操作后：yyy

这种非常明确的状态对比。

#### 原则 4：高风险操作必须明确写出“不变的部分”

例如：

- 重置绑定不会删除历史
- 归档不会删除历史事件
- 维护模式不会停止采集
- 暂停会停止采集

这些“不会发生什么”，和“会发生什么”一样重要。

---

### 11.2 接入准备页草案

接入准备页是 Node 创建后的第一落点。  
它不是一个普通详情页，而是一个：

> **“让节点真正进入系统”的状态化工作台**

---

#### 11.2.1 页面状态分层

我建议接入准备页至少支持 4 个明显子状态：

##### A. 未开始接入

语义：

- Node 已创建
- Token 已生成
- 还没有任何 agent 尝试接入

页面重点：

- 展示 token
- 展示安装步骤
- 强调当前绑定状态 = 未绑定

##### B. 接入尝试中

语义：

- 已经有 agent 发起过尝试
- 但还没形成有效绑定闭环

页面重点：

- 最近一次尝试时间
- 最近一次尝试结果
- 若失败，给出简短失败摘要

##### C. 已绑定但尚未形成有效观测

语义：

- token + 指纹绑定已经成功
- 但系统还没有看到稳定心跳/有效样本

页面重点：

- 告知“已绑定，但还未进入稳定监控”
- 强调下一步是等待心跳与样本

##### D. 接入完成

语义：

- 已绑定
- 已有有效心跳
- 已有 observation 成功入库

页面重点：

- 清楚告诉用户“这台机器已正式接入”
- 主 CTA 切换为：查看节点详情

---

#### 11.2.2 页面布局建议

建议分成 4 个区块：

##### 区块 A：节点基础卡

展示：

- 显示名称
- 地区 / 城市
- 供应商
- 生命周期状态
- 监控运行状态
- 绑定状态

##### 区块 B：接入凭证区

展示：

- token（受控显示）
- 复制按钮
- 最近生成时间

并提供：

- 再生成 token（高风险，次级入口）

##### 区块 C：接入步骤区

建议以固定步骤的方式展示：

1. 在服务器上安装 agent
2. 写入该节点专属 token
3. 启动 systemd 服务
4. 等待首次同步与绑定完成

##### 区块 D：状态反馈区

展示：

- 最近一次尝试结果
- 最近一次失败摘要
- 当前指纹状态
- 最近一次心跳时间
- 首批样本是否已到达

---

#### 11.2.3 这个页面不应承担的职责

不建议在接入准备页里塞：

- 完整 Node 趋势图
- 所有异常列表
- 探针负载摘要
- 复杂配置编辑

因为这页的唯一目标是：

> **完成“从创建 Node 到 Node 真正进入系统”的闭环。**

---

### 11.3 绑定冲突处理页 / 冲突卡片草案

这是系统里最有辨识度的一块状态化交互。

---

#### 11.3.1 触发条件

当中心检测到：

- token 正确
- 但机器指纹与当前绑定不一致

则 Node 进入：

- `指纹变更待确认`

并应在：

- 节点列表
- 节点详情
- 事件流

都给出明显可见性。

---

#### 11.3.2 列表页的轻提示

节点列表页里，这类对象应有：

- 明显异常标记
- 可被“绑定异常”筛选出来
- 状态摘要中显示：`等待绑定确认`

但不建议在列表页里直接做最终处理。  
列表页只应该承担“发现问题”，不承担“拍板风险动作”。

---

#### 11.3.3 详情页中的冲突处理卡片

建议在 Node 详情页头部下方，出现一个固定优先级很高的卡片。

##### 卡片应展示

- 当前绑定摘要
- 新指纹首次尝试时间
- 最近冲突次数
- 是否仍在持续尝试

##### 卡片应回答两个问题

1. 这是不是原机器重装后回来？
2. 还是另一台机器误用了旧 token？

---

#### 11.3.4 可执行动作

##### A. 确认重绑定

页面文案建议强调：

- 将用新指纹接管该 Node
- 历史数据保留在原 Node 上
- 后续 observation 会继续并入该 Node

##### B. 拒绝新指纹

页面文案建议强调：

- 保留当前绑定关系
- 拒绝本次新接入尝试
- 不修改历史

##### C. 重置绑定

页面文案建议强调：

- 清除当前绑定关系
- 回到等待重新绑定状态
- 不删除历史

---

#### 11.3.5 为什么这里不做更多动作

不建议 v1 提供：

- 基于冲突自动新建 Node
- 自动拆分历史
- 自动克隆节点配置

因为这些都会把“节点身份”这件事做复杂。  
v1 更适合坚持：

- 识别冲突
- 人工确认
- 明确决策

---

### 11.4 维护模式确认流草案

维护模式是高频动作，但它的语义很容易被误解，所以即使做轻确认，也应有清楚的状态说明。

---

#### 11.4.1 Node 进入维护模式

建议确认弹层至少明确写出：

##### 当前

- 监控运行状态：启用

##### 操作后

- 监控运行状态：维护中

##### 影响

- 继续采集主机指标
- 继续执行探针
- observation 正常入库
- 不参与异常判定
- 不更新健康状态
- 不发 Telegram

##### 不会发生

- 不会删除历史
- 不会停止 agent
- 不会改变生命周期状态

---

#### 11.4.2 Target 进入维护模式

建议语义一致，但对象改为 Target：

- 继续执行该 Target 下的 ProbeItem
- 结果入库
- 不参与异常 / 健康 / 通知

##### 为什么必须写清楚“继续执行”

因为很多人会本能把“维护中”理解成“停掉了”。  
而我们已经冻结的语义是：

> **维护中 = 继续观测，但不解释。**

这必须在交互层反复强调。

---

#### 11.4.3 退出维护模式

退出维护模式可以比进入更轻。  
但也建议给一句轻量提示：

> 退出后，新的 observation 将重新参与异常判定、健康状态更新与通知。

这样能帮助用户预期：
- 一旦恢复启用，问题可能重新出现

---

### 11.5 暂停确认流草案

暂停比维护更重，因为它会真正打断数据连续性。

---

#### 11.5.1 Node 暂停监控

确认弹层建议至少明确：

##### 操作后影响

- 停止主机指标采集
- 停止该节点承担的探针执行
- 不参与异常 / 健康 / 通知

##### 明确提示

- 趋势图会从此开始出现空档
- 如果该节点承担其他 Target 的执行任务，这些目标可能失去部分视角

##### 为什么暂停比维护需要更强确认

因为它不仅改变通知行为，还改变：

- 数据链路
- 探针执行范围实际能力
- 历史连续性

---

#### 11.5.2 Target 暂停

确认弹层建议明确：

- 停止该 Target 下所有 ProbeItem 的执行
- 不再产生新的目标 observation
- 不参与异常 / 健康 / 通知
- 历史保留

##### 为什么要和归档区分

因为暂停的语义是：

> 以后还可能恢复

而归档的语义是：

> 退出活跃对象集合，但保留历史

---

### 11.6 Target 归档确认流草案

Target 归档是高风险但常见动作。  
所以它既不能太重，也不能太随意。

---

#### 11.6.1 确认弹层建议展示

##### 当前

- 运行状态：启用 / 维护中 / 暂停

##### 操作后

- 运行状态：已归档

##### 影响

- 目标不再出现在活跃目标默认视图中
- 不再继续日常探测
- 不参与异常 / 健康 / 通知
- 历史 observation 与事件保留

##### 恢复说明

- 如需恢复，应先从归档状态恢复到暂停，再显式启用

---

#### 11.6.2 为什么归档确认必须有“恢复路径”说明

因为：

- 归档不是删除
- 归档不是停用后永远消失

它本质上是：

> **保留历史、退出活跃工作集**

这个心智必须在确认时就建立。

---

### 11.7 Node 退役确认流草案

Node 退役和 Target 归档看起来相似，但语义不同。

---

#### 11.7.1 建议在详情页中作为状态编辑动作存在

不建议在列表页直接暴露“退役”。

#### 11.7.2 确认弹层建议明确

##### 操作后

- 生命周期状态变为 `已退役`

##### 影响

- 该 Node 不再视为活跃舰队成员
- 历史数据保留
- 默认不再进入日常使用语义

##### 不自动发生的事情

- 不等于删除
- 不等于清空历史
- 不等于一定立即移除 agent

##### 恢复说明

- 若后续恢复，建议先恢复为 `观察中`

---

### 11.8 重置绑定确认流草案

这是 Node 上风险最高的动作之一。

---

#### 11.8.1 确认弹层建议展示

##### 当前

- 当前绑定状态
- 当前指纹摘要

##### 操作后

- 绑定状态回到 `未绑定`
- 等待新的合法绑定

##### 影响

- 不删除 Node 历史
- 不改变生命周期状态
- 后续旧 agent 继续同步可能失败或触发新冲突

##### 为什么必须红区强确认

因为一旦误点：

- 你会打断一个正在正常工作的绑定关系
- 后续接入会进入更混乱状态

---

### 11.9 空状态原型的统一风格建议

我建议所有空状态都遵循统一模板：

1. 先解释当前没有什么
2. 再解释为什么这不是错误
3. 再给出唯一最推荐下一步动作

例如：

#### 首页空状态

- 当前还没有节点与目标
- 这不是异常
- 推荐先创建第一个 Node

#### Target 无 ProbeItem 空状态

- 这个入口已存在
- 但还未配置观测方式
- 推荐添加第一个 ProbeItem

#### Node 未绑定空状态

- 节点对象已建立
- 但 agent 还没真正接入
- 推荐复制 token 并完成 agent 安装

---

### 11.10 这一节的结论

如果把这一节冻结，v1 的关键状态化页面可以浓缩成一句话：

# **重要状态切换必须先解释当前状态、目标状态和影响范围，再允许用户确认。**

更具体一点：

- 接入准备页是 **Node 创建后的首要工作台**
- 绑定冲突必须有明确处理卡片，不藏在普通编辑里
- 维护模式必须反复强调“继续采集，但不解释”
- 暂停必须强调“会中断数据连续性”
- 归档与退役都应明确“保留历史，但退出活跃工作集”
- 重置绑定必须是红区强确认

这会显著降低后续系统的误操作风险，也会让这套设计在真正实现时更像“稳的工具”而不是“靠记忆理解的后台”。

---

## 12. 状态恢复、误操作回滚与“不可逆边界”草案

这一节的目标，是把这套系统里最容易在后期实现时被忽略的一层补齐：

> **哪些状态切换是轻量可逆的，哪些动作只能通过“恢复路径”间接回退，哪些边界原则上不应该被伪装成可撤销。**

如果这一层不提前收紧，后面很容易出现：

- 误操作后只能靠删对象“补救”
- 归档、退役、暂停、删除被混成一类
- 用户以为某动作是可逆的，实际上会破坏历史语义
- UI 到处放“恢复”按钮，但不同对象根本没有统一恢复规则

---

### 12.1 状态恢复设计的总原则

我建议 v1 明确采用下面 4 条总原则。

#### 12.1.1 优先“状态回退”，不优先“数据回滚”

v1 的主对象大多都带状态机，所以误操作后的首选补救方式应该是：

- 从 `维护中` 回到 `启用`
- 从 `暂停` 回到 `启用`
- 从 `已归档` 回到 `暂停`
- 从 `已退役` 回到 `观察中`

而不是：

- 删除对象重建
- 修改历史 observation
- 清空事件流掩盖误操作

这条原则很重要，因为你的系统非常强调：

- 历史连续性
- 趋势判断
- 生命周期判断
- 误操作后的可解释性

---

#### 12.1.2 “可恢复”不等于“无痕撤销”

我建议 v1 明确区分这两件事：

- **可恢复**：状态可以沿预定义路径回到可用状态
- **无痕撤销**：仿佛这个动作从未发生过

v1 应只追求第一种，不追求第二种。

例如：

- Target 被归档后，可以恢复到 `暂停`
- Node 被退役后，可以恢复到 `观察中`

但：

- 归档事件不会消失
- 退役事件不会消失
- 期间未采到的数据不会被“补造”出来

这会让系统在长期使用中保持可信。

---

#### 12.1.3 越接近历史事实层，越不应该支持“回滚”

我建议把可逆性明确分层：

- **配置层 / 状态层**：大多可恢复
- **派生层 / 通知层**：可通过后续事件闭环，但不应强行抹掉
- **原始事实层**：原则上不可回滚

例如：

- 可以恢复 Node 的监控运行状态
- 可以恢复 Target 的运行状态
- 可以通过“恢复正常”事件闭合一次异常生命周期
- 但不应该回头删除一批已经真实入库的 observation

---

#### 12.1.4 UI 必须把“恢复路径”显式化

也就是说，恢复不应该靠用户猜。

当一个对象进入：

- `暂停`
- `已归档`
- `已退役`
- `指纹变更待确认`

详情页或确认层里都应该明确告诉用户：

- 当前停在什么状态
- 下一步允许怎么恢复
- 不允许直接跳到哪里

这样后面系统才不会变成“只有设计者自己知道怎么操作”。

---

### 12.2 v1 的动作可逆性分层

我建议把 v1 的动作按恢复难度分成 3 层。

---

#### 12.2.1 第一层：轻量可逆动作

这类动作应该满足：

- 可快速切回
- 不改变历史归属
- 不破坏对象身份
- 不需要复杂恢复流程

包括：

- 进入维护模式 / 退出维护模式
- 暂停监控 / 恢复监控
- Target 暂停 / 恢复
- ProbeItem 启用 / 停用
- 编辑标签

这类动作的恢复语义应偏“就地切回”。

---

#### 12.2.2 第二层：需要明确恢复路径的动作

这类动作虽然可以恢复，但不应一键无脑切回。

包括：

- Target 归档
- Node 退役
- 确认重绑定
- 重置绑定

它们的特点是：

- 会改变对象在系统中的语义位置
- 历史仍保留
- 恢复要走显式路径

例如：

- `已归档 -> 暂停 -> 启用`
- `已退役 -> 观察中`

---

#### 12.2.3 第三层：原则上不以“恢复”为主设计的动作

包括：

- 删除 Node / Target / ProbeItem
- 未来如果有：清理历史 observation / 清理事件记录

这些动作在 v1 中不应被当作常规管理手段。

也就是说：

> **v1 的恢复设计，不应该围绕“删错了怎么办”展开，而应该围绕“状态走错了怎么办”展开。**

---

### 12.3 Node 的恢复路径草案

Node 是状态最厚的对象，所以它的恢复路径必须最清楚。

---

#### 12.3.1 生命周期状态恢复

##### `待接入`

它不是需要“恢复”的状态，而更像起点。

如果误把一个活跃 Node 调回 `待接入`，我建议 v1 **不要支持普通状态编辑直接回退到 `待接入`**。

原因是：

- `待接入` 代表还没形成有效接入闭环
- 一个已经长期活跃的 Node 回到这个状态，语义会很脏

所以设计上更合理的是：

> `待接入` 只作为创建后早期状态，不作为常规回退目标。

---

##### `在用`

它可以从：

- `观察中`
- `不续费`

恢复回来。

这代表：

- 你重新确认这台机器适合作为活跃舰队成员

---

##### `观察中`

我建议把它看作 Node 生命周期的**默认恢复中间态**。

原因是：

- 它比 `在用` 更保守
- 比 `已退役` 更活跃
- 适合承接误操作或策略变化后的回流

因此：

- `已退役 -> 观察中`
- `不续费 -> 观察中`
- 甚至某些特殊修正场景，也优先回到 `观察中`

都很合理。

---

##### `不续费`

它可以恢复到：

- `观察中`
- `在用`

但我建议 UI 上更推荐：

- 先回到 `观察中`

因为“不续费”本质上是策略判断，而不是物理事实；恢复时先进入重新评估，更符合你的使用方式。

---

##### `已退役`

`已退役` 我建议仍然视为**近似终态**，但不是绝对不可恢复。

恢复建议路径固定为：

- `已退役 -> 观察中`

而不是：

- `已退役 -> 在用`

##### 为什么不能直接回到 `在用`

因为退役意味着：

- 这台机器已退出活跃舰队语义
- 可能已经不再可信
- 可能已有较长时间未参与日常观测

所以恢复时更合理的是：

> **先重新纳入观察，再决定是否恢复活跃服役。**

---

#### 12.3.2 监控运行状态恢复

##### `维护中`

恢复路径：

- `维护中 -> 启用`

这是最轻的一类恢复。

##### 恢复后的语义

- 新 observation 重新参与异常判定
- 健康状态重新可被更新
- Telegram 通知重新启用

##### 不应发生的误解

- 维护结束不会回填“维护期间本该触发的告警”
- 维护期间 suppressed 的异常不会被追溯补发

---

##### `暂停`

恢复路径：

- `暂停 -> 启用`

我建议 v1 不支持：

- `暂停 -> 维护中`

因为这条路径语义不够自然。更清晰的路径应该是：

- 先 `暂停 -> 启用`
- 如有需要再 `启用 -> 维护中`

##### 为什么这样更稳

因为：

- `暂停` 是停止采集
- `维护中` 是继续采集但静默

这两者的运行时意义差别太大，直接跳转容易让用户误解“是不是会自动恢复数据链路”。

---

#### 12.3.3 绑定状态恢复

##### `未绑定`

恢复路径其实不是状态切换，而是重新完成接入闭环：

- 新的合法 agent 持 token 接入
- 首次有效同步成功
- 状态进入 `已绑定`

##### `指纹变更待确认`

恢复路径应明确只有两种：

- 确认重绑定 -> `已绑定`
- 拒绝新指纹 -> 保持原绑定 `已绑定`

不建议再长出更多中间态。

##### 为什么“拒绝”也算恢复路径的一部分

因为它恢复的是：

> **对象身份语义的稳定性**

而不一定是“新接入成功”。

---

### 12.4 Target 的恢复路径草案

Target 没有 Node 那么厚的生命周期，所以恢复路径应更简单、更一致。

---

#### 12.4.1 `维护中`

恢复路径：

- `维护中 -> 启用`

语义与 Node 保持一致：

- observation 恢复参与异常 / 健康 / 通知
- 不追溯补发维护期间 suppressed 告警

---

#### 12.4.2 `暂停`

恢复路径：

- `暂停 -> 启用`

这表示：

- 该 Target 下 ProbeItem 恢复执行
- 目标重新回到活跃观测集合

---

#### 12.4.3 `已归档`

恢复路径固定建议为：

- `已归档 -> 暂停`

而不是：

- `已归档 -> 启用`

##### 为什么必须先回暂停

因为归档代表：

- 目标退出活跃工作集
- 可能已经较长时间不再被持续观测
- 直接恢复启用容易让一个旧入口突然重新参与探测与通知

先恢复到 `暂停`，能让你在重新启用前做最小复查：

- host / base_port 是否仍然对
- ProbeItem 是否仍合理
- 执行节点标签是否仍适合

---

### 12.5 ProbeItem 的恢复与误操作边界

ProbeItem 的设计目标是轻，所以恢复语义也应保持轻。

---

#### 12.5.1 启停是完全可逆动作

- `enabled -> disabled`
- `disabled -> enabled`

都属于轻量恢复路径。

##### 适合场景

- 暂时不需要 TLS 检查
- 某个 HTTP 检查参数待调整
- 某个 ProbeItem 影响过大，先停掉观察

---

#### 12.5.2 删除不应被视为“普通恢复方式”

我建议 v1 明确：

- ProbeItem 删除只适用于误建
- 如果一个 ProbeItem 已经承载了较长历史，优先停用，不优先删除

##### 为什么

因为删除会打断：

- 目标下观测方式的连续性
- 相关历史上下文
- 事件与状态变化的解释链条

所以 v1 应优先鼓励：

> **停用，而不是删除。**

---

### 12.6 误操作回滚的统一策略草案

我建议 v1 用统一的“误操作回滚”哲学，而不是每个对象各玩各的。

---

#### 12.6.1 对轻量可逆动作，优先提供“立即反向操作”

例如：

- 进入维护后，提供明显的“退出维护”
- 暂停后，提供明显的“恢复启用”
- ProbeItem 停用后，提供明显的“重新启用”

这类动作不需要发明复杂 undo 系统。

---

#### 12.6.2 对中等风险动作，优先提供“恢复路径提示”

例如：

- Target 已归档：提示“可先恢复到暂停，再显式启用”
- Node 已退役：提示“可恢复到观察中”
- 绑定冲突：提示“可确认重绑定 / 拒绝新指纹”

重点不是做一个魔法撤销键，而是让用户清楚：

- 怎么回
- 能回到哪
- 不能直接回到哪

---

#### 12.6.3 对高风险动作，不提供“伪撤销”

例如：

- 删除对象
- 清理历史（如果未来支持）

不应设计成：

- 点完删除，再弹一个几秒倒计时“撤销”

因为这会制造一种错觉：

> **系统好像对历史类动作也支持随意后悔。**

这不符合 v1 的“历史可信”原则。

---

### 12.7 “不可逆边界”草案

这一部分我建议明确写进设计里，避免后续实现时为了“体验顺手”偷偷做脏。

---

#### 12.7.1 原始 observation 不可回滚

一旦 observation 作为事实成功入库，原则上就不应该被当作普通 UI 动作去回滚或删除。

##### 原因

因为它代表的是：

- 某个时间点确实发生过的观测
- 不是用户配置，也不是前端表单状态

如果这个边界被打破，后面你会越来越难相信：

- 图表
- 趋势
- 事件流
- 异常判定历史

---

#### 12.7.2 事件记录原则上不做“抹除式回滚”

例如：

- 进入维护模式
- 退出维护模式
- 归档
- 退役
- 重置绑定

这些动作一旦发生，其事件记录就应被保留。

恢复之后，正确做法是：

- 产生新的恢复事件

而不是：

- 把旧事件删掉，假装没发生过

---

#### 12.7.3 通知不做“撤回型语义”

对于 Telegram，我建议 v1 明确：

- 发送过的通知不会被“撤回”
- 正确的闭合方式是后续发恢复/修正信息

##### 为什么

因为 Telegram 不是事务型 UI，而是外部信道。

一旦发出，系统唯一可靠的做法是：

> **用后续事件把语义闭合，而不是假装上一条没发过。**

---

#### 12.7.4 数据缺口一旦成立，不应被掩盖

如果本地缓冲打满，导致 observation 永久丢失，那么：

- `gap event` 应保留
- 趋势图上的缺口应保留

后续即使对象状态恢复正常，也不意味着：

- 这段缺口可以被“恢复操作”覆盖掉

##### 原因

因为缺口表达的是：

> **那段时间系统没有完整事实。**

这是一个必须被保留的真相。

---

### 12.8 UI 上如何表达“可恢复”和“不可恢复”

我建议在交互层明确做出区分，而不是靠文档说明。

---

#### 12.8.1 可恢复对象要有明确下一步动作

例如：

- Node `维护中` -> 显示“退出维护”
- Node `暂停` -> 显示“恢复监控”
- Target `已归档` -> 显示“恢复到暂停”
- Node `已退役` -> 显示“恢复到观察中”

---

#### 12.8.2 不可直达的路径要显示为禁用并解释

例如：

- `已归档` Target 不应直接显示“恢复启用”
- `已退役` Node 不应直接显示“恢复在用”
- `暂停` Node 不应直接显示“转为维护中”

如果这些路径在 UI 里完全不可见，用户会困惑；如果直接允许，又会污染状态语义。

最好的方式是：

- 允许看到
- 但置灰
- 并给出一句解释

这和你在别的项目里偏好的“显示但置灰非法项”也是一致的。

---

#### 12.8.3 危险不可逆动作要进入危险区

例如：

- 删除 Node / Target / ProbeItem
- 重置绑定

建议统一进入详情页底部的危险区，避免和一般恢复动作视觉混淆。

---

### 12.9 恢复后的事件闭合语义

这一点我建议也写清楚：

> **恢复动作的价值，不只是把状态切回来，还要让历史上“知道它后来恢复了”。**

例如：

- Node 从 `暂停 -> 启用`
- Target 从 `已归档 -> 暂停`
- Node 从 `已退役 -> 观察中`

都应形成新的状态变化事件。

这样后续你看事件流时，会很容易理解：

- 什么时候停了
- 什么时候恢复了
- 恢复是回到什么状态，而不是简单“没事了”

---

### 12.10 这一节的结论

如果把这一节冻结，可以把 v1 的恢复与不可逆边界浓缩成一句话：

> **v1 优先恢复状态，不回滚事实；优先闭合历史，不伪造无痕撤销；越接近 observation 和事件层，越不应支持“假装没发生过”。**

更具体一点：

- 维护 / 暂停 / ProbeItem 启停属于轻量可逆动作
- 归档 / 退役 / 绑定处理属于“有恢复路径，但不无痕”的动作
- 删除不是日常管理手段
- observation、事件、通知、数据缺口都不应被恢复动作抹掉
- UI 必须把恢复路径和不可达路径显式表达出来

这样后面即使真正实现，这套系统也会天然更稳：

- 不靠删除补救状态错误
- 不靠掩盖历史制造“干净感”
- 不会因为可逆性设计混乱而把对象语义做脏


---

## 13. 批量操作、筛选持久化与“工作台视图”草案

这一节的目标，是把这套系统从“单对象设计合理”推进到“多对象日常使用也顺手”。

因为你真实面对的不是：

- 1 台机器
- 1 个目标
- 1 次状态切换

而是：

- 一批观察中节点
- 一批低配节点
- 一批已决定不续费但仍在运行的节点
- 一批同类入口需要统一静默、统一暂停、统一归档

如果这一层不提前设计，后面即使单对象详情页做得很好，日常使用还是会变成：

- 不断重复点相同操作
- 筛选条件每次重输
- 首页看完之后没有真正的工作台入口

---

### 13.1 设计原则

我建议 v1 在批量操作和工作台能力上坚持 4 条原则。

#### 13.1.1 批量操作只服务高频、低歧义动作

也就是说，v1 可以支持：

- 批量进入维护
- 批量退出维护
- 批量暂停
- 批量恢复
- 批量加标签
- 批量移除标签

但不应该支持：

- 批量改 host
- 批量改供应商
- 批量改 Probe 参数
- 批量重置绑定
- 批量删除

原因很简单：

> **批量能力应该减少重复劳动，而不是放大误操作半径。**

---

#### 13.1.2 筛选持久化应先于自定义仪表盘

v1 不需要：

- 多 dashboard
- 拖拽式工作台
- 卡片自由布局
- 自定义首页模板

但非常适合先支持：

- 保存筛选条件
- 保存排序方式
- 保存默认列表视角

因为对你来说，真正高频的是：

> **反复查看同一批对象，而不是反复搭仪表盘。**

---

#### 13.1.3 工作台视图应该是“保存好的列表入口”，不是“第二套首页”

也就是说，工作台视图更适合长这样：

- `观察中节点`
- `不续费但仍启用监控`
- `当前严重目标`
- `TLS 即将到期`

点进去后，本质上还是：

- 节点列表
- 目标列表

只是带着保存好的过滤与排序语义。

这能最大程度复用前面已经设计好的列表页，而不会把系统再长出一层“工作台产品”。

---

#### 13.1.4 批量能力必须明显弱于单对象能力

我建议 v1 明确：

- 单对象详情页 = 最完整能力入口
- 列表页批量操作 = 为高频一致动作服务

也就是说：

- 批量可以做“少而准”
- 不能试图覆盖所有单对象动作

否则后面系统会越来越像企业后台的批处理中心。

---

### 13.2 Node 批量操作草案

Node 是最典型需要批量操作的对象，因为你会频繁遇到一整批机器具有相同管理意图。

---

#### 13.2.1 建议支持的 Node 批量操作

##### A. 批量进入维护模式

适合：

- 某批机器准备迁移
- 某地区节点要统一观察
- 某供应商节点正在做集中调整

##### B. 批量退出维护模式

适合：

- 某次维护窗口结束

##### C. 批量暂停监控

适合：

- 一批低优先级节点暂时不再纳入日常观测
- 某批节点暂时不想承担探针责任

##### D. 批量恢复监控

适合：

- 暂停后重新纳入工作集

##### E. 批量添加标签 / 移除标签

适合：

- 给一批节点标记 `低配`
- 给一批节点标记 `国内参考探针`
- 去掉过期的管理标签

---

#### 13.2.2 不建议支持的 Node 批量操作

##### A. 批量修改生命周期状态

例如：

- 批量设为 `已退役`
- 批量设为 `不续费`

我建议 v1 默认不开放，原因是：

- 生命周期状态是管理判断
- 风险高
- 很容易把策略误操作放大

如果后续真要加，也应是高确认特性，而不是 v1 默认能力。

##### B. 批量重置绑定

绝对不建议。这个风险太高。

##### C. 批量删除

不建议。和 v1 的“优先状态化，不优先删除”直接冲突。

---

### 13.3 Target 批量操作草案

Target 也适合少量批量动作，但比 Node 更克制。

---

#### 13.3.1 建议支持的 Target 批量操作

##### A. 批量进入维护 / 退出维护

适合：

- 一批入口正在升级
- 一批参考目标暂时不想参与异常体系

##### B. 批量暂停 / 恢复

适合：

- 一批低优先级目标暂时停止观测

##### C. 批量归档

我建议：

- **可以支持**
- 但必须是强确认
- 且确认层要明确显示数量与影响范围

因为对 Target 来说，归档是比删除更正常的管理动作。

##### D. 批量标签编辑

适合：

- 给一组目标打 `高优先级`
- 给一组目标打 `临时参考`

---

#### 13.3.2 不建议支持的 Target 批量操作

- 批量改 host
- 批量改 `base_port`
- 批量改执行节点标签
- 批量改 ProbeItem 参数
- 批量删除

这些动作的语义都太“结构性”，不适合 v1 先做。

---

### 13.4 ProbeItem 批量操作草案

我建议 v1 **默认不做 ProbeItem 跨 Target 批量操作**。

原因是：

- ProbeItem 不是一等管理对象
- 它天然依附于 Target
- 一旦做跨 Target 批量，很容易把配置层复杂度拉高

如果后面需要，最多也只考虑：

- 在单个 Target 内对多个 ProbeItem 做启停

而不是全局 ProbeItem 管理台。

---

### 13.5 推荐标签体系草案

前面我们已经把标签定成一等能力，但还没把“推荐标签体系”收出来。这里我建议补齐。

我建议 v1 的标签使用遵循一个原则：

> **结构化字段负责稳定事实，标签负责灵活语义。**

也就是说：

- 地区 / 城市 -> 用结构化字段
- 供应商 -> 用结构化字段
- 是否 `service` / `china_reference` -> 用类型字段

而标签主要承载下面三类语义：

---

#### 13.5.1 能力类标签

适合 Node：

- `核心`
- `低配`
- `仅基础监控`
- `服务探针`
- `国内参考探针`

这类标签最适合参与：

- 执行范围
- 默认规则覆盖
- 工作台筛选

---

#### 13.5.2 策略类标签

适合 Node / Target：

- `高优先级`
- `待观察`
- `临时`
- `手动关注`

这类标签最适合参与：

- 日常筛选
- 工作台视图
- 你的主观管理判断

---

#### 13.5.3 专题类标签

适合临时组织：

- `迁移中`
- `新购测试`
- `线路对比`
- `证书重点关注`

这类标签我建议允许自由使用，但不建议把它们升格成系统级结构字段。

---

#### 13.5.4 不建议的标签滥用

我建议 v1 设计里明确提醒：

- 不要用标签重复表达 `region` / `city` / `provider`
- 不要用标签代替运行状态
- 不要用标签代替生命周期状态

也就是说：

- `维护中` 应是状态，不应只是标签
- `已退役` 应是状态，不应只是标签

这样模型才不会越来越脏。

---

### 13.6 筛选持久化草案

这是我认为 v1 很值得加入的一层能力。

---

#### 13.6.1 建议持久化的内容

对于节点列表和目标列表，我建议都支持保存：

- 过滤条件
- 排序方式
- 是否仅看异常
- 是否仅看严重 / 告警

但我建议 v1 **不保存列布局**、**不保存页面组件布局**。

##### 为什么这样收

因为你的高频需求是：

> **我想反复回到某一批对象的工作视图**

而不是：

> **我想搭一个高度可编排的页面系统**

---

#### 13.6.2 持久化范围建议

我建议 v1 先只支持：

- 节点列表视图保存
- 目标列表视图保存

不建议对：

- 首页
- 事件页
- 设置页

做“保存视图”。

---

### 13.7 工作台视图草案

基于前面的筛选持久化，我建议 v1 把“工作台视图”定义成：

> **保存好的列表视图快捷入口**

而不是新的页面系统。

---

#### 13.7.1 建议内置的 Node 工作台视图

##### A. 当前异常节点

默认筛选：
- 当前健康状态为 `关注/告警/严重`

##### B. 当前严重节点

默认筛选：
- 当前健康状态为 `严重`

##### C. 观察中节点

默认筛选：
- 生命周期状态 = `观察中`

##### D. 不续费但仍启用监控

默认筛选：
- 生命周期状态 = `不续费`
- 监控运行状态 = `启用/维护中`

##### E. 国内参考探针节点

默认筛选：
- 标签包含 `国内参考探针`

---

#### 13.7.2 建议内置的 Target 工作台视图

##### A. 当前异常目标

默认筛选：
- 健康状态为 `关注/告警/严重`

##### B. 当前严重目标

默认筛选：
- 健康状态为 `严重`

##### C. 国内参考目标

默认筛选：
- `target_type = china_reference`

##### D. TLS 证书关注目标

默认筛选：
- 当前存在 TLS 预警类异常

##### E. 已归档目标

默认筛选：
- 运行状态 = `已归档`

---

#### 13.7.3 用户自定义工作台视图

我建议 v1 **允许少量自定义视图**，但必须克制：

- 本质仍是保存筛选条件
- 不允许自定义组件布局
- 不允许自定义图表模板
- 不允许每个视图定义独立规则

也就是说：

> **自定义视图 = 保存好的列表过滤器，而不是自定义 dashboard。**

---

### 13.8 批量操作的确认强度草案

我建议批量动作的确认强度按动作类型分层。

---

#### 13.8.1 轻确认批量动作

适合：

- 批量进入维护
- 批量退出维护
- 批量添加标签
- 批量移除标签

建议：
- 明确显示对象数量
- 明确显示作用范围
- 不必进入危险红区

---

#### 13.8.2 强确认批量动作

适合：

- 批量暂停 Node
- 批量暂停 Target
- 批量恢复大量对象
- 批量归档 Target

建议：
- 明确显示对象数量
- 明确显示影响
- 需要二次确认

---

#### 13.8.3 v1 不开放的批量危险动作

- 批量退役 Node
- 批量重置绑定
- 批量删除

这三类我建议直接不做。

---

### 13.9 这一节的结论

如果把这一节冻结，可以把 v1 的多对象工作流浓缩成一句话：

> **v1 可以有批量能力，但只服务高频、低歧义动作；工作台视图本质上是保存好的列表视图，而不是第二套首页或企业级 dashboard。**

更具体一点：

- Node / Target 支持少量高价值批量操作
- ProbeItem 不做全局批量管理
- 标签承担灵活语义，但不替代结构字段与状态
- 支持列表筛选持久化
- 提供内置工作台视图 + 少量用户自定义视图
- 不做多 dashboard，不做拖拽编排

这样后面你在真实使用中会得到一个非常实用的效果：

- 首页看问题
- 工作台视图接手日常处理
- 单对象详情负责深入判断

而不会把整个系统做成一个重后台。

---

## 14. v1 设计完成定义与实施前冻结包草案

这一节不是继续扩功能，而是明确：

> **做到什么程度，v1 设计就算完成；还剩下的内容属于实施前微调，而不再是结构性缺口。**

---

### 14.1 我对“v1 设计完成”的判断

基于目前已经收出来的内容，我建议把当前状态定义为：

# **v1 结构设计已完成，进入评审冻结阶段**

原因是：

- 系统定位已清楚
- 架构拓扑已清楚
- 数据链路已清楚
- 核心对象模型已清楚
- 状态机已清楚
- 异常与通知语义已清楚
- 页面与交互原型已清楚
- 接入、绑定、补传、缺口语义已清楚
- 状态恢复与不可逆边界已清楚
- 多对象工作台与批量操作边界也已清楚

换句话说：

> **后面还需要继续审，但现在剩下的主要是参数微调和实现前冻结，不再是“系统到底应该长什么样”这种结构性问题。**

### 14.2 仍属于“实施前微调”而非“设计未完成”的项目

我建议明确把下面这些内容降级为：

> **实施前微调项**

而不是继续阻塞 v1 设计完成。

包括：

- CPU / load / 内存 / 磁盘 / inode 的具体阈值微调

### 14.4 实施前还建议做的最后一轮审阅

我建议在真正进入别的项目实施前，只再做一轮**冻结式审阅**，而不是继续无限发散。

这轮审阅重点只看 5 件事：

1. **对象模型是否还要改**
2. **状态机是否还要改**
3. **默认阈值草案是否需要整体偏保守 / 偏激进**
4. **交互原型里是否存在明显高风险误操作点**
5. **有没有任何内容在不知不觉中越过了 v1 边界**

只要这 5 件事过关，我认为就不应该再继续发散新功能了。

- v1 之后的 backlog
