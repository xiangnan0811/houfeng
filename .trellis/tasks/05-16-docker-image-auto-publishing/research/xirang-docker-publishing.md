### Code Patterns

#### Workflow trigger patterns

`publish-images.yml` publishes only on GitHub Release publication or explicit maintainer dispatch:

- `release: types: [published]` at `.github/workflows/publish-images.yml:3-6`.
- `workflow_dispatch` requires both `version` and `source_ref` inputs at `.github/workflows/publish-images.yml:7-16`.
- The workflow rejects prerelease releases before building at `.github/workflows/publish-images.yml:46-50`.
- Concurrency is keyed by `publish-images-${{ github.ref }}` and does not cancel in-progress publication at `.github/workflows/publish-images.yml:18-20`.

`dockerhub-description.yml` is separate from image publishing:

- It runs on pushes to `main` when `README.md` or the workflow itself changes, plus manual dispatch at `.github/workflows/dockerhub-description.yml:3-10`.
- It only needs `contents: read` at `.github/workflows/dockerhub-description.yml:12-13`.

Release creation is handled separately by Release Please on `main` pushes:

- `.github/workflows/release-please.yml` exists and runs on push to `main`; the image workflow itself is not a `push` or `pull_request` workflow.

#### Docker Hub login and push method

The publishing workflow uses official Docker actions and a two-stage digest-then-manifest publication pattern:

- Docker Hub login uses `docker/login-action` with `registry: docker.io`, `secrets.DOCKERHUB_USERNAME`, and `secrets.DOCKERHUB_TOKEN` at `.github/workflows/publish-images.yml:91-96` and again for manifest publishing at `.github/workflows/publish-images.yml:206-211`.
- Metadata is generated by `docker/metadata-action` at `.github/workflows/publish-images.yml:98-110` and `.github/workflows/publish-images.yml:213-225`.
- Per-platform builds use `docker/build-push-action` with `context: .`, `file: deploy/allinone/Dockerfile`, `platforms: ${{ matrix.platform }}`, and `outputs: type=image,name=${{ env.REGISTRY_IMAGE }},push-by-digest=true,name-canonical=true,push=true` at `.github/workflows/publish-images.yml:114-124`.
- Images are scanned by Trivy before formal tags/manifest are created; HIGH/CRITICAL vulnerabilities fail the build at `.github/workflows/publish-images.yml:130-139`.
- Per-platform digest files are uploaded as short-lived artifacts at `.github/workflows/publish-images.yml:141-155`.
- The publish job downloads digests and creates the multi-arch tagged manifest with `docker buildx imagetools create` at `.github/workflows/publish-images.yml:227-276`.
- Build provenance attestation is pushed to registry using `actions/attest-build-provenance` at `.github/workflows/publish-images.yml:291-296`.

The current image name is hard-coded:

- `REGISTRY_IMAGE: docker.io/linnea7171/xirang` in build and publish jobs at `.github/workflows/publish-images.yml:42-43` and `.github/workflows/publish-images.yml:163-164`.

#### Platform and runner policy

The workflow builds a multi-architecture image with native runners:

- Matrix includes `linux/amd64` on `ubuntu-latest` and `linux/arm64` on `ubuntu-24.04-arm` at `.github/workflows/publish-images.yml:34-41`.
- Comments state the intent is to avoid running arm64 Node/CGO builds under QEMU, and to avoid creating official tags before scanning succeeds at `.github/workflows/publish-images.yml:112-113`.

#### Tag policy

Release/manual version resolution:

- Release runs derive the version from `github.event.release.tag_name`; manual runs derive it from `github.event.inputs.version` at `.github/workflows/publish-images.yml:70-74` and `.github/workflows/publish-images.yml:185-189`.
- Leading `refs/tags/` and leading `v` are stripped at `.github/workflows/publish-images.yml:76-77` and `.github/workflows/publish-images.yml:191-192`.
- The cleaned version must match strict `X.Y.Z` semver at `.github/workflows/publish-images.yml:84-87` and `.github/workflows/publish-images.yml:199-202`.

Generated Docker tags:

- `vX.Y.Z` at `.github/workflows/publish-images.yml:103-104` and `.github/workflows/publish-images.yml:218-219`.
- `X.Y.Z` at `.github/workflows/publish-images.yml:105` and `.github/workflows/publish-images.yml:220`.
- `latest` only when the event is a non-prerelease `release` at `.github/workflows/publish-images.yml:106` and `.github/workflows/publish-images.yml:221`.
- Manual rebuilds do not update `latest`; this is also reflected in the build summary message at `.github/workflows/publish-images.yml:307`.

#### Labels and summary

OCI labels include source repository, source commit, and version:

- `org.opencontainers.image.source`, `org.opencontainers.image.revision`, and `org.opencontainers.image.version` at `.github/workflows/publish-images.yml:107-110` and `.github/workflows/publish-images.yml:222-225`.
- The workflow emits a GitHub step summary with version, source ref, commit, digest, latest-update status, tags, and platform digests at `.github/workflows/publish-images.yml:298-312`.

#### Secrets and variables used

Image publishing uses:

- `DOCKERHUB_USERNAME` secret at `.github/workflows/publish-images.yml:95` and `.github/workflows/publish-images.yml:210`.
- `DOCKERHUB_TOKEN` secret at `.github/workflows/publish-images.yml:96` and `.github/workflows/publish-images.yml:211`.

Docker Hub description sync uses:

- `DOCKERHUB_USERNAME` as a fallback metadata username at `.github/workflows/dockerhub-description.yml:26`.
- `DOCKERHUB_DESCRIPTION_USERNAME` optional override at `.github/workflows/dockerhub-description.yml:27`.
- `DOCKERHUB_DESCRIPTION_PASSWORD` for Docker Hub metadata update at `.github/workflows/dockerhub-description.yml:28` and `.github/workflows/dockerhub-description.yml:49`.
- The workflow skips metadata sync gracefully if description credentials are missing at `.github/workflows/dockerhub-description.yml:31-41`.

Release Please uses:

- `RELEASE_PLEASE_TOKEN` in `.github/workflows/release-please.yml` for release PR/release automation; this is adjacent release infrastructure, not part of Docker Hub login/push.

#### PR-vs-main behavior

- Image publishing does not run on pull requests and does not run directly on `main` push. It runs on published releases or manual dispatch only (`.github/workflows/publish-images.yml:3-16`).
- `latest` is only updated by non-prerelease release publication, not by PRs, direct main pushes, or manual rebuilds (`.github/workflows/publish-images.yml:103-106`, `.github/workflows/publish-images.yml:218-221`, `.github/workflows/publish-images.yml:307`).
- Docker Hub description sync runs on `main` pushes touching README/workflow and on manual dispatch, not on PRs (`.github/workflows/dockerhub-description.yml:3-10`).
- Release Please runs on `main` pushes to prepare/release versions; this can indirectly lead to the release event that triggers image publication, but the publish workflow remains release-gated.

#### Dockerfile and compose relationship in xirang

- Xirang publishes from `deploy/allinone/Dockerfile`, not a root Dockerfile (`.github/workflows/publish-images.yml:118-120`).
- The all-in-one Dockerfile builds web assets from `web/` and a backend binary from `backend/` (`deploy/allinone/Dockerfile:1-24`), then packages them behind nginx with additional runtime services and storage paths (`deploy/allinone/Dockerfile:40-88`).
- The current public README describes the official image as `docker.io/linnea7171/xirang` and deploys via `docker compose pull` / `docker compose up -d` (`README.md:19-36`).
- The current README tells production operators to pin `IMAGE_TAG=vX.Y.Z` (`README.md:27-32`).

### Houfeng Constraints Mapping

Given Houfeng’s stated constraints and local files:

- Image repository should be `docker.io/linnea7171/houfeng`, matching `/Users/weibo/Code/houfeng/compose.yaml:1-4`.
- Houfeng should use the root `/Users/weibo/Code/houfeng/Dockerfile`, not Xirang’s `deploy/allinone/Dockerfile`; the Houfeng Dockerfile builds only web assets and the `houfeng-center` binary (`/Users/weibo/Code/houfeng/Dockerfile:1-51`).
- Houfeng compose pulls `linnea7171/houfeng:latest` for the center and runs PostgreSQL separately (`/Users/weibo/Code/houfeng/compose.yaml:1-33`).
- Houfeng’s container boundary is center+web only; no agent image should be added because agents remain host-level systemd binaries and are not part of Docker/Compose deployment.
- Houfeng `.dockerignore` already excludes local secrets, `.trellis`, local compose data, and build artifacts (`/Users/weibo/Code/houfeng/.dockerignore:7-63`), which is relevant because the publish workflow should use root build context.

What can be copied into Houfeng as a pattern:

- Release-published plus manual-dispatch trigger shape.
- Strict semver normalization from `vX.Y.Z` to `X.Y.Z`.
- Docker Hub login via `docker/login-action` using `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN`.
- `docker/metadata-action` tags for `vX.Y.Z`, `X.Y.Z`, and release-only `latest`.
- Multi-arch matrix for `linux/amd64` and `linux/arm64` with digest-first pushes and final `buildx imagetools create` manifest.
- Trivy scan before formal manifest/tag publication.
- OCI labels and build summary.
- Optional separate Docker Hub description sync workflow if Houfeng wants Docker Hub README metadata automation.

What should not be copied directly into Houfeng:

- Do not use Xirang’s image name `docker.io/linnea7171/xirang`; Houfeng’s target is `docker.io/linnea7171/houfeng`.
- Do not use `file: deploy/allinone/Dockerfile`; Houfeng’s Dockerfile is at repository root.
- Do not copy Xirang’s all-in-one nginx/supercronic/SQLite/backup runtime assumptions; Houfeng’s compose topology is center+PostgreSQL, and the Houfeng Dockerfile already serves the built SPA through the Go center.
- Do not add an agent container/image target; Houfeng’s project instructions keep agents as outbound systemd binaries installed on hosts.
- Do not assume Xirang’s `latest` avoidance on manual rebuilds matches Houfeng automatically; it is an observed Xirang behavior to consider against Houfeng’s `compose.yaml` currently pulling `latest`.
