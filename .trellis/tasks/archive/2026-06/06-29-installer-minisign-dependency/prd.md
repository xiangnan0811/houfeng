# Fix agent installer minisign dependency

## Goal

Explain and harden the real-environment failure mode where a center deployed as `v0.55.0` generates an agent upgrade command that fails on Debian 11 because `minisign` is missing and unavailable from the default apt repositories.

The code path that fixes missing-`minisign` recovery already shipped in `v0.55.1` and is present in current `main` / `v0.55.2`; this task captures the root cause, verifies current behavior, and adds operator-facing troubleshooting guidance for stale `v0.55.0` commands.

## Confirmed Facts

- Real target host:
  - Debian 11 bullseye, `x86_64`, Linux kernel `5.10.0-8-amd64`.
  - `apt install minisign` and `apt-get install minisign` both fail with `E: Unable to locate package minisign`.
- The failing command was generated by a center upgraded to `v0.55.0` and had this relevant shape:
  - `sudo sh "$tmp_installer" --server-url 'https://center.example.com' --enrollment-token-stdin --version 'v0.55.0' --release-repo 'xiangnan0811/houfeng'`
  - It did **not** include `--install-missing-deps`.
- `v0.55.0` installer code fails immediately on missing `minisign`:
  - `command -v minisign >/dev/null 2>&1 || fail "minisign is required to verify release checksums"`
- `v0.55.1` and current `v0.55.2` include:
  - installer flags `--install-missing-deps` and `--no-install-missing-deps`;
  - pinned upstream `minisign` 0.12 bootstrap with SHA256 verification;
  - generated install/upgrade commands that include `--install-missing-deps`;
  - signed checksum manifest verification remains mandatory.
- GitHub Releases `v0.55.1` and `v0.55.2` both contain Linux agent binaries, `sha256sums.txt`, and `sha256sums.txt.minisig`.

## Root Cause

The immediate failure is expected for `v0.55.0`: the generated command and embedded installer predate the missing-dependency recovery path. Debian 11 does not provide `minisign` from the checked default repositories, so the old installer cannot progress unless the operator manually installs a compatible verifier from another source.

The durable fix is not to install distro packages manually on every host. The center should be upgraded to a version containing the installer recovery path (`v0.55.1+`, currently `v0.55.2`), then the operator should regenerate the MonitoringInstance install/upgrade command so the newly served `/api/agent/install.sh` and the generated command both contain missing-dependency recovery behavior.

## Requirements

- Document the stale `v0.55.0` command shape and explain why it fails on Debian 11-style hosts.
- Make the recommended operator path explicit:
  - upgrade the center image/binary to `v0.55.1+` or the latest published patch release;
  - restart the center;
  - regenerate the MonitoringInstance install/upgrade command;
  - confirm the command contains `--install-missing-deps`;
  - run the regenerated command on the target host.
- Keep the security contract clear: do not recommend checksum-only install, disabling signature verification, editing `sha256sums.txt`, or using unsigned agent binaries.
- Mention the emergency fallback only as a temporary workaround for old centers: manually install a trusted `minisign` binary or run a regenerated command from a fixed center; do not rely on `apt install minisign` as a universal answer.
- Verify that current code still generates `--install-missing-deps` and that installer tests cover the recovery path.
- Preserve the existing installer contract in `.trellis/spec/backend/directory-structure.md`; update spec only if the investigation reveals a missing durable rule.
