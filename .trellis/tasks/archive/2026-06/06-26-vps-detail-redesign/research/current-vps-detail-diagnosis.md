# VPS 详情页现状诊断

## 诊断目标

本诊断先回答“为什么现在的 VPS 详情页会让用户觉得乱”，再讨论怎么改。重点不是评价视觉风格，而是拆解每个默认可见区域是否服务单台 VPS 的核心使用任务：

- 当前这台 VPS 应该保留、观察、迁移、取消，还是补证据？
- 当前最大的风险或阻塞是什么？
- 用户下一步应该做什么？
- 其他事实如何支撑判断，而不是抢占判断主线？

## 当前默认页面结构

代码入口：

- `web/src/pages/VPSDetailPage.tsx`
- `web/src/pages/vps-detail/VPSDetailHero.tsx`
- `web/src/pages/vps-detail/VPSDecisionBoard.tsx`
- `web/src/pages/vps-detail/VPSIPQualitySection.tsx`

默认渲染顺序：

1. `VPSDetailHero`
   - VPS 名称。
   - 生命周期、使用状态、续费决策、监控实例数量 badges。
   - 顶部操作：处理决策、组合决策、创建订阅、延长有效期、创建/升级 agent、更多菜单、VPS 列表。
   - provider / location 元信息。
2. 全局反馈：
   - 订阅读取错误。
   - 决策更新 notice + 可能的后续链接。
3. `VPSDecisionBoard`
   - 标题：资产判断。
   - 操作：调整决策、进入组合决策。
   - 下一步动作。
   - 五个证据卡：当前决策、订阅证据、监控实例证据、资料质量、上下文。
   - 条件性生命周期联动提示。
   - 四个摘要卡：续费与成本、监控实例证据、服务与域名、最近历史。
   - 资料摘要。
4. `VPSIPQualitySection`
   - 独立 IP 质量标题区。
   - 质量评分大卡。
   - 风险信号、解锁概览、证据覆盖。
   - 解锁状态 badges。
   - 完整报告链接。
5. `成本卡片`
   - 原币种价格。
   - 基准月成本。
   - 下次续费。
   - 支付方式。
   - 汇率 / 续费方式 signals。
6. 条件性 `VPSLifecycleCard` + `ActionConfirmationModal`
   - 归档/恢复确认时才出现。
7. `Modal`
   - 承载全部详情和编辑表单。

## 已确认的历史背景

当前页面不是一开始就这样堆出来的。历史任务显示：

- `05-19-optimize-vps-detail-information-architecture` 已经明确目标：让 VPS 详情页从“字段与区块平铺”收敛为资产运营判断页。
- 当时已经把低价值资料、服务/域名全量表、历史、基础资料等后置到 Drawer，默认视图只保留判断摘要。
- `06-09-ip-quality-dashboard-page` 已经确定低频报告模式：VPS 详情页摘要 + 独立完整报告页。
- 后续提交又把新 summary 直接追加进默认视图：
  - `cd5a68a feat(subscriptions): add VPS cost center` 在 `VPSDetailPage.tsx` 中新增独立 `成本卡片`，插入 86 行 JSX 和 41 行样式。
  - `eb4cbcf feat: show ip quality in web ui` 新增 `VPSIPQualitySection` 并在默认页中渲染。
  - `fd1d8a3 feat(web): detail-page IA — decision boards, drawer→modal sweep` 新增 `VPSDecisionBoard`。

结论：页面再次混乱的根因不是“没有做过 IA”，而是默认视图缺少一个持续生效的承载边界。后续每个新能力都以“摘要卡”的名义重新进入默认页面，最终摘要本身变成新的信息堆叠。

## 核心根因

### 1. 默认视图没有单一主任务

用户进入 VPS 详情页时，同时看到：

- 顶部的“处理决策”。
- 顶部的“组合决策”。
- 资产判断里的“调整决策”。
- 资产判断里的“进入组合决策”。
- 下一步动作中的“查看监控实例”。
- 生命周期提示里的“打开取消/退役工作台”。
- 成本卡片里的“订阅工作台”或“快速创建订阅”。
- IP 质量里的“查看完整 IP 质量报告”。

这些入口都合理，但它们在默认视图中同权出现，导致用户无法判断“系统建议我现在先做哪一件事”。主 CTA 被多个次 CTA 稀释。

### 2. 同一事实被多层重复表达

订阅/成本至少出现三次：

- `VPSDecisionBoard` 的五个 evidence 卡里有 `订阅证据`。
- `VPSDecisionBoard` 的四个摘要卡里有 `续费与成本`。
- `VPSDetailPage.tsx` 还单独渲染 `成本卡片`。

监控实例至少出现三次：

- Hero badge：`N 个监控实例`。
- Evidence 卡：`监控实例证据`。
- 摘要卡：`监控实例证据`。
- 详情入口 Drawer 里又是完整 `监控实例证据`。

服务/域名至少出现两次：

- Evidence 卡里的 `上下文`：`N 服务 · N 域名`。
- 摘要卡里的 `服务与域名`。

资料也出现两次：

- Evidence 卡里的 `资料质量`。
- 底部 `资料摘要`。

重复本身不是问题，问题是这些重复没有分工：没有区分“状态信号”“解释证据”“详情入口”“编辑入口”。用户看到的是同一组概念不断换名字出现。

### 3. 摘要卡的语义边界失效

历史 IA 的方向是“默认视图只保留支持判断的摘要，全量内容后置”。但现在摘要区已经出现三类互相竞争的摘要：

- `VPSDecisionBoard` 内部的 evidence summary。
- `VPSDecisionBoard` 内部的 operation cards。
- `VPSIPQualitySection` / `成本卡片` 作为独立 section summary。

每个子域都认为自己只是“摘要”，但用户看到的是多个完整 section。摘要数量过多以后，与全量平铺在体验上没有本质差别。

### 4. 状态色和风险等级没有稳定地表达优先级

顶部 badges、evidence 卡、operation 卡、IP 质量、生命周期提示都使用状态色和边框。红/橙/紫/蓝/绿色同时出现。

当前问题：

- `已取消自动续费` 是续费事实，但被 critical badge 表达，容易被理解成系统级危险。
- `IP 质量 80` 是可接受分数，但独立大卡和 accent 边框给了它很强的视觉权重。
- `资料可用` 是低风险事实，却和真正风险卡同一组视觉结构。
- 生命周期联动提示一旦出现，会以 alert 色整块插入判断区域，容易抢过“下一步动作”。

状态色应该服务优先级，而不是所有子域都用自己的色彩体系表达“我重要”。

### 5. 页面语言偏内部实现，不偏用户任务

典型文案：

- “生命周期联动待需要时读取”
- “普通 CRUD 不会隐式联动”
- “资产判断证据状态”
- “Target”
- “证据覆盖”
- “低频采集”

这些表达对开发者和系统模型有意义，但用户的问题通常是：

- 这台机器现在有没有风险？
- 为什么建议先看监控异常？
- 已取消自动续费会不会导致停机？
- 我需要补什么信息？
- 点这个按钮会不会删除监控数据？

页面应该把内部模型翻译成用户任务语言。内部术语可以留在详情、诊断或帮助文本里，但不应该成为默认视图的主解释。

### 6. 信息密度和视觉密度方向相反

当前 UI 是高密度工具风格，但默认视图使用了大量 bordered cards：

- 大 panel 包小 cards。
- 小 cards 内还有 badge、header、summary、footer。
- IP 质量又是一个大 panel 包 score card、facts cards、badge strip。
- 成本卡片又是四个 cards + signal strip。

高密度工具应减少不必要框体，让用户扫描关系和优先级。现在的密度主要来自“边框数量”和“小字数量”，不是来自清晰的信息结构。

### 7. Drawer 策略只解决了全量内容，没解决首屏摘要膨胀

当前页面已经把基础资料、监控实例详情、服务、域名、历史等全量内容后置到 `Modal`。这是正确方向。

但首屏仍保留了过多摘要，说明问题已经从“全量表格平铺”演化为“摘要平铺”。下一轮重构不能只是继续把东西挪进 Drawer，还要定义：一个事实是否有资格在默认视图中独立成区。

### 8. 测试锁定了旧的混乱形态

`VPSDetailPage.test.tsx` 当前断言：

- 默认页必须有 `资产判断`、`下一步动作`、`资产判断证据状态`。
- 默认页必须有 `续费与成本`、`监控实例证据`、`服务与域名`、`最近历史`、`资料摘要`。
- 默认页必须有 `IP 质量` 和完整报告链接。
- 测试没有显式断言 `成本卡片` heading，但当前实现默认渲染它。

这意味着后续“清理默认视图”必须更新测试，而不是被旧测试要求绑住。测试应改为验证用户任务和关键能力保留，而不是验证旧模块名字必须出现。

## 分区级诊断

### Hero

当前价值：

- 快速确认这是哪台 VPS。
- 展示生命周期、使用状态、续费决策、监控实例数量。
- 提供高频操作入口。

问题：

- 主操作过多，顶部一眼看到 5 个按钮加更多菜单。
- `处理决策` 和 `组合决策` 同时存在，但二者关系不清楚。
- `创建订阅`、`延长有效期`、`升级/重新接入 agent` 都是情境操作，却在所有状态下作为顶部同级按钮出现。
- `VPS 列表` 与核心操作混在一起。

初步方向：

- Hero 只保留身份、关键状态和一个由决策模型给出的主 CTA。
- 次级操作统一进更多菜单或对应证据区。
- 返回列表使用低权重位置，不与主操作竞争。

### Asset Decision Board

当前价值：

- 已有纯函数 `buildVPSDecisionModel`，能根据订阅、监控实例、资料、决策状态计算下一步动作。
- 这是页面最接近“用户任务”的模块。

问题：

- Board 内部自己又包含三层结构：下一步动作、五证据卡、四摘要卡、资料摘要。
- `调整决策` 和 `进入组合决策` 与 Hero 重复。
- Evidence 卡和 operation 卡重复字段，且视觉权重接近。
- 生命周期联动插入在 board 中间，使“下一步动作”不再唯一。

初步方向：

- 保留“下一步动作”作为主轴，但把 evidence 从 5 个等权 cards 改为按严重程度排序的紧凑证据列表。
- 把 “operation cards” 与独立成本/IP summary 合并成一个统一的 `判断依据` 或 `证据概览` 区，不再多层摘要。
- Board 中只保留一个主 CTA；组合决策作为次级入口。

### Lifecycle Coordination

当前价值：

- 当 VPS 处于取消、迁移、已取消自动续费或 preview 有 warning/blocker 时，提示用户需要处理订阅、监控实例、Target。

问题：

- 文案偏系统实现。
- 位置在 DecisionBoard 内部，容易被理解为与所有状态都同等重要。
- “需核对”badge 和红/橙边框可能抢过真正的 next action。

初步方向：

- 只在取消/迁移/待处理状态下作为主 CTA 或紧邻主 CTA 的阻塞提示显示。
- 对普通状态完全隐藏。
- 文案改为“取消前还需要处理哪些关联对象”。

### IP Quality

当前价值：

- IP 质量是 VPS 是否适合流媒体、AI、普通业务的重要证据。
- 已有完整独立报告页，详情页只需提供摘要和跳转。

问题：

- 当前独立 section 视觉重量过大，接近一个完整驾驶舱摘要。
- `质量评分 80`、风险信号、解锁概览、证据覆盖、badge strip 一起出现，超出了“支撑判断”的默认需求。
- 它不直接回答当前页面主问题，除非当前决策确实受 IP 质量影响。

初步方向：

- 默认视图中 IP 质量降为证据列表中的一行或一个低权重证据组。
- 只突出异常：高风险、严重风险、报告过期、采集失败、服务解锁受阻。
- 正常/可接受时显示 `IP 80 · 2 风险 · 3 可用` 级别摘要，完整报告通过链接进入。

### Cost Card

当前价值：

- 订阅成本是续费判断的核心事实。
- 支付方式、基准货币、汇率状态对成本复盘有价值。

问题：

- `VPSDecisionBoard` 已经展示续费与成本，独立 `成本卡片` 再次展示同一领域。
- `支付方式`、`汇率日期`、`年化成本` 对首屏判断未必同权重要。
- heading `成本卡片` 是实现/组件语言，不是用户任务语言。

初步方向：

- 移除独立默认 section。
- 成本只在核心证据中展示最关键项：月成本、续费日、续费方式/已取消自动续费。
- 支付方式、汇率、年化成本进入订阅详情入口或成本 drawer。

### Services / Domains / History / Facts

当前价值：

- 服务/域名表示 VPS 业务上下文。
- 历史表示之前为什么做过某个判断。
- Facts 是基础台账和编辑来源。

问题：

- 当前默认视图里它们已经不是全量表，但仍重复出现在 evidence 和 operation cards 中。
- `服务与域名`、`最近历史`、`资料摘要` 在首屏都是同权 cards，容易让用户误以为它们和异常/续费风险同等优先。

初步方向：

- 只在默认视图提供一条上下文摘要：例如 `承载 0 服务 / 0 域名 · 最近 2 条判断记录`。
- 有异常或缺口时升级为显著证据；正常时保持低权重。
- 全量内容继续通过 drawer/modal 或独立页面入口查看。

## 移动端风险

当前 CSS 在窄屏下会把：

- Hero actions 变成多按钮 grid。
- Decision evidence 由 5 列变 2 列。
- Operation cards 由 4 列变 2 列。
- IP 质量 facts 由多列变 2 列/1 列。

这意味着移动端不是信息减少，而是同样信息变成长滚动。移动端应使用同一内容优先级规则，而不是仅靠响应式换列。

## 当前最重要的设计约束

后续方案应先定义默认视图资格：

1. 能决定当前下一步动作的内容，默认可见。
2. 能解释当前下一步动作的 3-5 条关键证据，默认可见。
3. 当前 VPS 的基本情况必须默认可见，但以紧凑摘要呈现，不展开为全量字段表。
4. 正常但低风险事实，只做低权重一行摘要。
5. 全量事实、编辑表单、诊断矩阵、历史列表进入 Drawer 或独立页面。
6. 危险操作只在用户触发时进入确认流程，不作为默认内容。
7. 每个事实在默认视图中只能承担一个角色：状态、证据、入口或反馈，不允许多处重复承担同一角色。

## 初步改进方向

不急于 mockup，但基于诊断可以先形成方向：

- 将页面默认视图收敛为：
  - Compact identity header。
  - Single decision command panel。
  - Prioritized evidence list。
  - Low-weight context strip。
  - Optional blocking lifecycle alert。
- 移除或合并默认独立 `成本卡片`。
- 将 `IP 质量` 从独立重 section 降级为证据行/紧凑摘要，完整报告保留独立路由。
- 顶部只保留一个主 CTA，其余操作进入更多菜单或对应详情入口。
- 更新测试，让测试断言“关键判断内容和能力保留”，而不是旧 section heading。

## 解决原则草案

这些原则用于后续设计，不代表已经定稿。

### 原则 1：默认视图只回答一个问题

默认视图的问题应是：

> 我现在应该怎么处理这台 VPS？

页面可以展示很多事实，但都必须服务这个问题。不能同时把默认视图做成账单页、监控页、IP 质量报告页、服务/域名台账和历史页。

同时，VPS 详情页仍必须让用户确认“这是哪台 VPS”。基本情况应默认可见，但表达为紧凑身份和事实摘要，而不是全量资料表。

### 原则 2：主 CTA 只能有一个

主 CTA 来自 `buildVPSDecisionModel` 的下一步动作，例如：

- 调整续费决策。
- 补录订阅。
- 创建/查看监控实例。
- 核对运行异常。
- 打开取消/退役工作台。
- 补充经验记录。

其他操作都降为次级入口。它们可以存在，但不能和主 CTA 抢同一层级。

### 原则 3：证据按优先级排序，不按领域平均分配

当前页面按领域分配位置：订阅、监控、资料、上下文、IP、成本各拿一块。这会自然膨胀。

新方案应按优先级排序：

1. 阻塞当前动作的事实。
2. 影响续费/迁移/取消判断的风险。
3. 缺失但需要补齐的证据。
4. 正常且可用的背景事实。
5. 低频详情入口。

### 原则 4：同一事实默认只出现一次

每个事实在默认视图里只能承担一个角色：

- 状态：放在身份区。
- 判断证据：放在证据列表。
- 操作入口：放在主 CTA 或次级菜单。
- 详情入口：放在低权重链接。

例如“订阅续费日”不能同时出现在 evidence 卡、续费卡、成本卡和提示文案中。

### 原则 5：正常事实降权，异常事实升权

不是每个子系统都需要固定展示一张卡。更合理的规则：

- 正常 IP 质量：一行摘要 + 报告链接。
- IP 高风险/报告失败/过期：升为显著证据。
- 有活跃异常监控实例：升为核心风险。
- 监控正常：只显示“监控正常 / 最近心跳”。
- 服务/域名为空：如果不影响当前判断，低权重显示；如果当前决策依赖业务上下文，再升权。

### 原则 6：危险和生命周期操作不常驻默认内容

归档、取消、退役、解除关联等操作需要明确确认，但不应该作为默认页面内容持续占位。它们应在：

- 主 CTA 判断出当前必须处理时出现。
- 用户从更多菜单主动触发时进入确认流程。
- 有 blockers/warnings 时显示紧凑阻塞提示。

### 原则 7：文案用用户任务语言，内部术语进详情层

默认视图文案应回答用户问题：

- “这会影响续费判断。”
- “取消前还有 1 个监控实例在运行。”
- “今天续费，且自动续费已取消。”
- “IP 质量可接受，完整报告可查看。”

内部术语如 `CRUD`、`Target`、`证据覆盖`、`联动` 可以留在详情、诊断或开发文档中，不应成为首屏主文案。

### 原则 8：新增子域必须先通过默认视图资格审查

未来再加入路由质量、性能基准、CPU/IO 趋势、超售判断等低频报告时，不能直接追加新的默认 section。必须先判断：

- 它是否改变当前下一步动作？
- 它是否是当前最高优先级风险？
- 能否折叠为证据列表中的一行？
- 是否已有独立详情页更适合承载？

这条原则是防止 VPS 详情页再次膨胀的关键。

### 原则 9：基础摘要与详情页分工明确

以 IP 质量为例：

- VPS 详情页展示基础判断摘要：例如评分、最高风险、解锁概览、报告时间、完整报告入口。
- IP 质量详情页承载 provider/service 矩阵、覆盖率、历史和诊断。

同样模式也适用于未来路由质量、性能基准等低频深度事实。默认页要能提示“是否需要关注”，但不承担完整分析。

## 已确认的默认基础情况字段

默认视图暂定展示：

- Provider。
- 地区 / 数据中心。
- 产品规格。
- IPv4 或 SSH Host。
- SSH 端口。
- 操作系统。
- 生命周期。
- 使用状态。
- 续费决策。
- 监控实例数。
- IP 质量一句话摘要。

默认不展示，进入“基础资料”弹窗：

- VPS ID。
- Provider ID。
- 订单号。
- IPv6。
- SSH 用户。
- 虚拟化。
- 标签。
- 备注。
- 归档时间。
