# 重构 VPS 详情页

## Goal

对 VPS 详情页做一次从用户实际使用体验出发的深度重构：先系统诊断当前页面为什么混乱，明确每一处显示的职责、优先级和取舍原则，再通过浏览器 mockup 验证新方案，最后才进入正式实现。

本任务不是简单美化或调 CSS。目标是让 VPS 详情页成为单台 VPS 的清晰资产判断工作台：用户进入页面后能快速知道当前结论、主要风险、缺什么证据、下一步该做什么，同时保留订阅、监控实例、IP 质量、服务/域名、历史和危险操作的完整能力，但不把所有内容同权重堆到默认视图里。

## Requirements

- 规划阶段必须先产出深度诊断，再进入新方案展示：
  - 诊断当前页面每个默认可见区域、状态标签、操作入口、文案和数据摘要的职责。
  - 区分必须首屏展示、可摘要展示、应进入弹窗/详情页、应只在特定状态显示、应删除或合并的内容。
  - 找出当前混乱的根因，而不是只罗列“页面太长/卡片太多”。
- 在诊断基础上提出解决原则和候选方向，经用户确认后再用 superpowers brainstorming 的视觉伴随流程制作浏览器 mockup。
- 新方案必须逐项考虑：
  - 首屏主任务和唯一主 CTA。
  - VPS 身份、生命周期、使用状态、续费决策、监控实例数量等状态的呈现顺序和语义。
  - 资产判断、订阅/成本、监控证据、生命周期联动、IP 质量、服务/域名、资料摘要、历史记录之间的层级关系。
  - 各类操作入口应该出现在主按钮、更多菜单、摘要卡、弹窗、独立报告页还是危险确认流程中。
  - 空态、读取失败、缺失事实、真实风险、危险操作不能混用同一种视觉强度。
- 保留现有业务能力和 API 合同，除非诊断证明某处必须改：
  - 续费决策、创建/更新订阅、延长有效期、接入/升级 agent、关联已有监控实例、编辑基础资料、记录经验、新增服务、新增域名、取消/退役、归档确认、IP 质量完整报告入口。
- 默认视图不能把所有子域 summary 同权重堆叠；每个默认可见模块都必须回答“这对当前 VPS 判断有什么用”。
- 默认视图仍必须展示当前 VPS 的基本情况。基本情况不是全量字段表，而是用户判断“这台机器是谁、在哪里买、在哪、怎么访问、当前处于什么状态”的紧凑事实摘要。
- 默认可见的 VPS 基本情况暂定包含：
  - Provider。
  - 地区 / 数据中心。
  - 产品规格。
  - IPv4 或 SSH Host。
  - SSH 端口。
  - 操作系统。
  - 生命周期。
  - 使用状态。
  - 续费决策。
  - 监控实例数。
  - IP 质量一句话摘要。
- 默认不展示、进入“基础资料”弹窗的字段：
  - VPS ID。
  - Provider ID。
  - 订单号。
  - IPv6。
  - SSH 用户。
  - 虚拟化。
  - 标签。
  - 备注。
  - 归档时间。
- IP 质量这类低频深度内容采用“详情页基础摘要 + 独立详情页面”模式：VPS 详情页展示足够判断是否需要关注的基础 IP 质量信息，完整 provider/service/诊断进入对应 IP 质量详情页。
- V15 已确定为 VPS 详情页主体结构与页面布局基准：综合基础信息、关联概览、单机台账继续保留，不重新推翻主体框架。
- IP 质量虽然已有 `/vps/:vpsId/ip-quality` 独立详情页，但 `/vps/:vpsId` 默认页下方仍必须展示大致 IP 质量情况，作为单台 VPS 概况的一部分；默认页只显示概况，不复制完整报告。
- VPS 详情页不能变成孤立展示页；它必须作为单台 VPS 的操作起点，清楚串起 IP 质量、订阅、监控实例、服务、域名、Target、资产历史和组合决策等关联页面/弹窗。
- 关联操作必须允许用户从当前 VPS 快速管理，也允许用户快速跳到深度页面；用户不应为了处理当前 VPS 再绕回列表页或从全局入口重新定位。
- 关联入口必须区分两类动作：
  - 快速管理：在 VPS 当前上下文内打开弹窗，完成创建、延长、记录、关联、编辑等单台操作。
  - 深度查看：跳转到对应完整页面，例如 IP 质量报告、监控详情、订阅中枢、Target 详情、组合决策。
- VPS 详情页内的所有功能和按钮，包括基础资料、接入/升级 agent、创建/更新订阅、延长有效期、服务详情、域名详情、资产历史、记录经验、取消/退役、新增服务、新增域名，都必须以居中弹窗/modal 展示；禁止使用抽屉，也禁止点击后在页面内新增一段区域来承载内容。
- `取消/退役` 不是直接执行取消，也不是常驻危险入口；它是一个需要先查看影响范围、再显式选择订阅/监控实例/探测对象处理方式、最后确认执行的联动工作流。
- `取消/退役` 入口必须由当前 VPS 状态驱动，并整合到顶部 `当前判断` 区域：只有续费决策、生命周期或已加载预览结果表明需要处理取消/迁移/退役影响时才显示处理按钮；稳定保留、正常续费、无取消意图的状态不展示该入口。
- `取消/退役` 不应作为中部独立工作区常驻展示，也不应作为 `更多` 菜单里的普通低频项常驻展示。状态不合适时，默认页不显示该能力；深链 `/vps/:id?workbench=cancellation` 可继续打开既有 modal 以支持外部流程。
- V17 已被用户确认为暂定实现基准：信息架构、页面结构和交互方式按 V17 走；配色、圆角、阴影、按钮、卡片、弹窗和状态样式不照搬 mockup，而是使用项目现有整体风格、设计 tokens、通用原子组件和 BEM 体系。
- 文案必须转向用户任务语言，避免把内部实现词（例如普通 CRUD、联动、证据状态）作为主解释。
- 视觉实现必须沿用当前 React/Vite SPA、现有 atoms、设计 tokens、BEM 和当前 `web/src/index.css` 体系，不引入新 UI 框架或 page-local CSS。
- mockup 只作为布局和交互验收材料，不作为生产视觉源文件。正式实现不得把 `.v17-*` 类名、mockup 硬编码颜色或 mockup CSS 直接复制到 `web/src`。

## Acceptance Criteria

- [ ] 任务规划包含当前页面深度诊断，覆盖默认可见区域、状态/风险语义、操作入口、文案、视觉层级、数据边界和移动端风险。
- [ ] 诊断明确列出根因、用户影响、对应代码位置、保留/合并/降级/删除建议。
- [ ] 在诊断被用户认可前，不制作最终 mockup、不开始正式页面实现。
- [ ] 浏览器 mockup 阶段至少展示首屏结构、信息层级、关键状态和主要操作路径，并允许用户先看效果再批准实现。
- [ ] 最终实现后，`/vps/:vpsId` 默认视图只展示高价值判断内容；完整服务/域名/历史/基础资料/低频报告仍能通过明确入口访问。
- [ ] 现有关键 workflows 不回归，并更新 `VPSDetailPage.test.tsx` / 相关测试覆盖新布局和操作入口。
- [ ] `取消/退役` 仅在对应状态下出现在顶部 `当前判断` 内，点击后打开居中 `取消/退役` modal 并加载影响范围预览；正常状态下默认页和 `更多` 菜单均不展示该入口。
- [ ] 通过 web lint、测试、build；如进入代码阶段，按 Trellis Phase 2/3 完成检查、spec 更新和提交。

## Confirmed Facts

- 用户明确认为当前 VPS 详情页“非常混乱，乱七八糟”，自己部署测试也无法接受；本任务必须以真实使用体验为核心，而不是只满足已有测试。
- 用户授权使用 superpowers brainstorming 视觉伴随，但要求先深度发现问题、寻求解决方案，再展示新方案。
- 用户大致接受“强约束单主线工作台”方向，但明确要求 VPS 详情页仍展示当前 VPS 的基本情况；其他深层内容可以通过跳转、弹窗等方式展示。
- 用户确认默认基本情况先展示：Provider、地区、产品规格、IPv4 或 SSH Host、SSH 端口、系统、生命周期、使用状态、续费决策、监控实例数、IP 质量一句话摘要；VPS ID、Provider ID、订单号、IPv6、SSH 用户、虚拟化、标签、备注、归档时间暂不默认展示。
- 用户指出 V1 mockup 的“下一步动作”区域占比过大。VPS 订阅期间 85% 以上时间不需要下一步动作；这种极少数时间才有用的内容不应在大多数情况下占据大面积。后续设计必须以稳定期为默认状态，异常/临期/缺证据时才升权展示处理动作。
- 用户指出下一步动作提示语太啰嗦，像文字堆砌的 PPT。后续文案必须短、克制、可扫描。
- 用户指出 V2 仍有问题：下一步动作、证据摘要、状态提醒都不应该各自占一整横排，尤其证据摘要和状态提醒承载信息有限；这些信息应合并进更紧凑的基础信息/关注项布局。
- 用户认为 V2 顶部状态行展示位置、规格、IP 质量等方式方向正确，但字段排布欠缺考虑：例如 IP 质量右侧有空余但放不下另一个状态，说明 grid 列宽和信息密度需要重新设计。
- 用户指出 V3 的“续费提醒”不应单独占用框体，应直接在“观测状态/观测证据”区域下显示。
- 续费时间显示规则：正常续费显示“X 天后续费”；超过 30 天显示“X 个月后续费”；超过一年也显示月数。已取消自动续费显示“已取消自动续费 · X 天/月后到期”，单位规则同上。
- “稳定观察”命名不准确，应改为“观测状态”或“观测证据”等表达。
- 用户要求停止局部细节反复，改为一次性从整体出发设计完整 VPS 详情页面。
- 用户指出 V7 中 VPS 综合基础信息右侧“观测状态”和下方“关联概览”内容高度重复。后续方案必须重新划清边界：顶部右侧只保留跨域判断摘要和续费/到期结论，不再列心跳、服务/域名、最近历史、报告时间这类来源事实；这些事实归入关联概览或对应详情入口。
- 用户指出 V9 中 VPS 综合基础信息底部的详情入口与下方关联概览几乎全部重复，仅多出 IP 质量；后续方案应删除顶部详情入口，并把 IP 质量纳入关联概览。
- 用户指出关联概览不应固定 2x2 卡片布局：当前左侧信息、右侧按钮导致中间大量空白。后续方案应改为更紧凑的自适应横向/多列概览，允许 5、7、8 个块自然排布，不担心小屏时单独一块占一行。
- 用户确认关联概览中“查看/管理”这类通用按钮可以去掉，改为点击卡片标题进入详情；延长、接入、记录等各卡片独有的临时管理动作可以保留，并以弹窗形式管理。
- 用户指出 V11 中标题下方的 provider、地区、IP pills 与事实 grid 重复，应删除。
- 用户指出最终页面不应出现 mockup 用的啰嗦说明文字；这些只属于评审辅助，不属于产品 UI。
- 用户指出 `调整决策`、`组合决策` 不应放在右侧判断摘要内；`调整决策` 可考虑放到 `基础资料` 左侧，`组合决策` 可进入 `更多` 菜单。
- 用户指出当前方案过于像中转页，背离“VPS 详情页”的字面意义；在保留综合基础信息和关联概览的基础上，页面下方还需要增加直接用于管理、查看、记录单台 VPS 的内容展示。
- 用户指出 V12 的右侧“当前判断”仍然文字过多、解释性太强；后续应改为短字段/短值，不写“证据足够”“保持低干扰”等主观解释句。
- 用户指出关联概览标题右侧“标题进入详情；只保留独有临时动作”属于画蛇添足；最终 UI 不应出现这类使用说明。
- 用户指出 V12 的详情工作区仍然啰嗦且内容不合适；后续应重新设计为结构化、可扫描的单台 VPS 台账，而不是散文式备注或说明。
- 本轮完整设计范围只包含 `/vps/:vpsId` 默认页本身；暂不展开设计 IP 质量详情页、监控详情页、服务/域名详情页、订阅页等后续页面。
- 用户确认 VPS 详情页大体框架按当前形式继续，但要求继续完善与 IP 质量等 VPS 详情子页、订阅页、监控页、服务/域名/Target、资产历史和本页各弹窗之间的关联与操作。
- 用户要求关联操作必须全盘考虑用户流程：既可以从当前 VPS 快速管理，也可以快速跳转到对应深度页面，而不是让用户从全局入口重新进入再查找当前 VPS。

  - `取消/退役工作台` 改为 `取消/退役`，`工作台` 属于内部形态，不应作为默认可见操作名。
- 用户确认下一步继续优化“VPS 详情页面下的其他详情页面”，明确不是外部的订阅、监控等全局页面。
