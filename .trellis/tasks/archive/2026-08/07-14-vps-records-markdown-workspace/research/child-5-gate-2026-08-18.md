## Budget headroom audit (asked before starting Child 6)

Question was whether zero headroom is an implementation defect or an unreasonable baseline. Neither:

- Every one of the nine CSS budget limits and all four bundle limits are pinned exactly at the
  measured value. That is the ratchet working as designed (`styling-guidelines.md`: 预算只能随有
  证据的清理降低), not a mistake.
- Route-private CSS is not an escape hatch: `productionCssBytesMax` / `productionCssGzipBytesMax`
  count every emitted stylesheet, and `sourceFilesMax: 26` blocks a 27th file. `LoginPage.css` is a
  grandfathered exception, explicitly called out as one.
- There is no meaningful dead CSS to reclaim. Measured ~12KB raw of apparently unreferenced rules
  across all partials; nearly all are dynamically composed `--tone` / `--state` modifiers, i.e. false
  positives. The reachability contract already forbids genuinely orphaned classes.
- Practical consequence for Children 6–8: compose pages from the existing `page.css` / `atoms.css`
  vocabulary and ship zero new CSS, which Child 5 proved is achievable for a whole workspace.
- The only limit raised in this child is `maxAsyncJsGzipBytes`, which has a written audited exception
  for the lazy `MarkdownPreview` chunk. Entry JS, entry CSS, and fonts were not raised.
