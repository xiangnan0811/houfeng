# Dashboard 美观与效率打磨

## 背景

用户再次要求继续推进 Dashboard。本轮目标不是让 Dashboard “能用”即可，而是达到更高的产品要求：美观、高效、用户体验良好。上一轮已经把首页从多区块堆叠收敛为状态栏 + 工作台，混乱感降低，但信息密度又变得偏薄，视觉层级仍偏工程化，缺少成熟服务器管理系统首页应有的扫描节奏与操作手感。

本轮不能回到旧问题：不要重新堆独立 KPI、Group 列表、最近事件列表或系统快捷入口详情列表。正确方向是“有节制地增加有效信息密度”：让每一层回答不同问题，并让用户快速完成判断与跳转。

## 用户目标

1. Dashboard 不只是可用，还要有明确的视觉品质。
2. 首页应高效，让用户进入后立刻知道系统状态、当前要处理什么、下一步去哪里。
3. 交互体验要自然，链接、列表、指标、上下文都应有明确点击意图和良好扫描路径。
4. 借鉴同类或相似系统的优点，但不为了差异化牺牲服务器管理系统的基础功能。

## 当前问题复盘

1. **前几轮过度依赖结构正确性**：测试证明旧区块没有回归，但不能证明页面“好看”或“好用”。
2. **从混乱走向偏稀疏**：当前只有状态栏、少量指标和一个工作台，信息没有乱，但运行感和管理感不足。
3. **视觉节奏仍不成熟**：状态栏、异常队列、运行上下文和管理入口都是线性块，缺少更细的层级、动作权重和列表扫描节奏。
4. **交互动作不够精炼**：异常队列存在两个相邻的详情入口，视觉上容易显得重复；顶部按钮和队列动作的优先级还可以更清楚。
5. **正常态概览不够像管理系统工作台**：需要保留库存、事件、通知等基础入口，但表达要紧凑，不恢复旧的“信息仓库”。

## 同类系统可吸收的原则

参考研究文件：`research/comparable-dashboard-patterns.md`。

提炼为候风 Dashboard 的约束：

1. **Overview 先回答状态，再进入诊断**：首屏优先展示全局状态、关键指标和需要处理的队列。
2. **Top-left / 首屏高优先级区域给最重要信息**：异常态把严重对象和处理入口放在最前，正常态把库存与事件入口放在工作台内。
3. **仪表盘要控制面板数量和视觉重量**：添加信息时优先做 line-based / compact surface，不新增同权卡片区。
4. **入口必须承接真实工作流**：Dashboard 上的对象、指标、上下文都必须深链到 Nodes / Targets / Events / Settings 的真实筛选或管理页面。
5. **视觉质量来自层级与密度，不是装饰**：使用现有令牌、状态色、边框和排版建立节奏，不做营销化 hero、不加装饰性背景。

## 方案

### 1. 状态栏打磨

保留现有 `FleetStatePanel` 结构，但优化呈现：

* 状态栏应像“指挥条”，视觉上比普通卡片更明确。
* 主标题、描述、生成时间、关键指标之间建立更紧凑的阅读层级。
* 关键指标从“小卡片”改为更轻的 compact rail/chip，减少卡片堆叠感。
* 主操作按钮保持清晰；次级入口不与主操作抢视觉焦点。

### 2. 异常队列打磨

异常态继续只展示一个 `当前需要处理` 工作台，但列表项要更像可处理队列：

* 扫描顺序固定为：状态 glyph → 对象身份 → 位置/新鲜度 → 异常级别与摘要 → 处理动作。
* 列表项应有足够点击面积、hover/focus 状态和紧凑边界。
* 次级详情链接文案改为更明确的处理动作，降低“两个进入链接”的重复感。
* 列表内长 ID、长 hostname、长摘要必须不撑破布局。

### 3. 运行上下文打磨

继续保留最多 3 个上下文入口，但降低视觉重量：

* `影响范围`、`库存状态`、`最近活动` 是同类系统常见 overview context，可以保留。
* 不能恢复独立 `Group 摘要` / `最近事件摘要`。
* 展示样式要更像工作台内的 context rail，而不是三个新卡片。

### 4. 正常 / 维护态工作台打磨

正常态不能只剩一句“当前没有活跃异常”，需要维持管理首页的基础价值：

* 保留节点、目标、事件、设置入口。
* 概览指标要可扫，但不能使用过大的 display 数字压过工作台。
* 运行上下文和管理入口要形成一组紧凑操作区，支持快速跳转。

### 5. 响应式与可访问性

* Desktop：状态栏两列；工作台内部保持清晰横向扫描。
* Tablet：指标和上下文可换行，不出现拥挤和截断错误。
* Mobile：所有列表、上下文、管理入口单列；按钮与链接可触达。
* 所有交互元素保留 focus-visible；链接 aria-label 继续表达真实目的。

## 验收标准

1. Dashboard 异常态仍只保留状态栏 + 一个主工作台，不恢复旧的独立 KPI / Group / Recent / shortcut 详情区。
2. 页面比当前版本信息更充实，但新增信息必须落在状态栏、处理队列、运行上下文或管理入口内。
3. 状态栏、异常队列、运行上下文、运行概览和管理入口的视觉层级明显改善，避免所有模块看起来同权。
4. 异常列表的主要处理路径更清楚，次级动作文案和布局更利于操作。
5. 正常 / 维护态仍能快速跳转节点、目标、事件和设置。
6. DashboardPage 测试继续覆盖旧 clutter 防回归、深链、上下文与队列行为；必要时增加文案/结构断言。
7. `docs/design/v2-houfeng/component-spec.md` 与 `.trellis/spec/web/state-and-data.md` 如有契约变化必须同步；纯 CSS 视觉变化至少在 component spec 中记录。
8. 通过：
   * `cd web && TMPDIR=/tmp npm run test -- --run src/pages/DashboardPage.test.tsx`
   * `cd web && TMPDIR=/tmp npm run test -- --run`
   * `cd web && npm run lint`
   * `cd web && npm run build`
   * `git diff --check`
9. 启动本地 dev server 并进行 Dashboard 视觉 sanity check，给出可访问 URL。

## 非目标

* 不新增 Dashboard API 字段。
* 不引入图表库、状态管理库、CSS 框架或 icon 依赖。
* 不做可配置 Dashboard、拖拽布局、自定义 widgets。
* 不恢复大型 Sparkline / KPI strip / Group list / recent event list。
* 不重写 Nodes、Targets、Events、Settings 页面。
